# AI Infra Skill 总体架构与重构计划

状态：首轮实施及脚本验收记录见文末。目标是提高领域分析准确性、能力组合效率、资产复用和交付质量。保留 methods、patterns、reports、catalog、prototypes、scripts 的现有组织，逻辑职责通过现有维护入口区分。

## 目标与架构

让开发者通过一个入口完成领域分析、讲解、浏览、对照或调查。用户可以指定布局、Pattern 和控件，领域事实、呈现意图和实现选择各有明确的维护者。保留五步 Workflow，按任务组合能力，不把现有六个 Skill 的数量或目录边界当作目标。

| 层 | 拥有的决策 | 主要交付 |
|---|---|---|
| 统一入口 | 任务识别、调用约束、能力路由、交付路径及验收编排 | 任务范围、必选与偏好、阶段选择、验收记录 |
| 领域分析 | 原生对象的含义、技术推导、版本及证据 | 可追溯的对象、关系、结论与未确认项 |
| 呈现设计 | 用户要定位、理解、核查、比较和操作什么 | 组件无关的呈现契约 |
| 界面设计与实现 | 布局、Pattern、组件绑定、视角、状态反馈及交互 | 可操作的视图与绑定记录 |
| 共享语义规范 | 跨域引用、关系合法性、适用范围和证据规则 | 共同的引用及映射规则 |
| 共享设计资产 | 正式图元、完整 Pattern、组件与可调用行为 | 版本化资产、声明入口及能力校验 |

领域与交付方式是两个独立维度。例如，模型、编译与运行分析可共同支撑一次实验对照；算子映射既可支撑渐进讲解，也可支撑源码调查。需要独立调用或独立验收的能力可以保留 Skill 入口，通用规则进入规范，领域资料进入参考，稳定的图形与交互进入资产。

## 现有六个 Skill 的职责调整

| 现有入口 | 调整 | 完成判据 |
|---|---|---|
| `ai-infra-investigation` | 保留为总入口。收敛到识别、约束、调度和验收，链接各层的规则维护源 | 可从同一入口选择直接回答、结构呈现／对照或交互调查。无需知道其他 Skill 的名字 |
| `llm-compute-diagrams` | 拆开领域分析、呈现设计和 Pattern 实现。模型与计算系统的推导归领域；渐进讲解、结构浏览归呈现；具体图解、泳道和交互归资产 | 同一领域输出可供讲解、对照或调查复用；旧图解的专用调用若保留，作为兼容入口调用这些能力 |
| `operator-mapping-investigation` | 保留独立领域分析。聚焦有效分支、索引、地址、布局、集合、API 和证据 | 可以只凭领域交付验收，也可把同一模型交给不同呈现路径 |
| `observability-design-style` | 将核心扩展为呈现设计。覆盖机制讲解、结构浏览、对照和调查；现有证据工作台是其调查模式 | 输出可描述定位、核查、操作和结果更新，文档无需先指定画布或 Inspector |
| `design-spatial-systems-ui` | 保留界面设计与实现能力。读取呈现契约和调用约束，选择布局、Pattern 和组件绑定 | 能独立修复已有页面的界面问题；对象定义、证据结论和操作规则仍由上游提供 |
| `ai-infra-glyphs` | 日常选型、variant、renderer、来源校验下沉为可调用资产。专项图元修复或来源审核可保留独立入口 | 常规页面生成可按声明复用正式图元；专项审核可追溯版本和来源 |

归并时逐项迁移原规则、参考与示例，区分覆盖重复、职责迁移和兼容保留。呈现设计决定用户点选后应去哪、核查什么。界面实现决定从哪个组件触发、如何定位和打开详情。Pattern 提供实际可复用的行为。

## 职责与维护源

| 规则 | 唯一维护源 | 生产者 → 消费者 |
|---|---|---|
| 跨域身份、关系、范围与证据 | 优先扩展 Methods 中现有共享契约或在其中按需放置 Cross-layer Identity Contract。执行前登记其与 Task Contract 的引用方向 | 领域分析写映射 → 校验脚本与呈现读取 |
| 原生类型、实例、Trace 与采集粒度 | 现有领域 Reference 与 Observation Model。正式对象表示与图元来源由 OBJECT-SYSTEM 和正式 Glyph Library 维护 | 领域输入与解析器 → 任务模型；Glyph Library → renderer |
| 任务交接、调用约束、路径 | Task Contract 维护任务记录要求；统一入口维护调用约束和路由 | 总入口及领域阶段 → 呈现、实现和验收 |
| 组件无关的呈现约定 | 现有 presentation-semantics.md；证据工作台保留调查模式特有的规则 | 呈现设计 → UI 实现与任务验收 |
| 调查动作与归档 | 呈现契约维护共性；candidate-review.md 验证 sync-1 的专用流程与示例 | 发起视图 → 回放或宿主执行 → 原调查记录 |
| 资产发现、实现和视觉 | catalog 管索引，Pattern 本身维护可用入口与行为；Systems UI 及正式 Glyph Library 分别维护界面和图元 | catalog／Pattern／规范 → UI 实现 |

Cross-layer Identity v1.1 draft 是评审输入，保留公共互操作定位。公共层拥有跨域引用和关系规则，领域规范拥有原生解释权。不要把逻辑能力机械拆成 specs、registries、adapters、schemas、tests 等目录。保留角色与基础 Kind 的区分、定义与实例的区分。Markdown 足以指导时使用 Markdown；机器交换或自动校验有真实消费者后才最小结构化。分发包所需公共引用由现有构建解析或生成版本化副本，并核对来源一致性。

## 各层最小输入输出

| 阶段或接口 | 最小输入 | 最小输出与兼容约束 |
|---|---|---|
| 统一入口 | 问题、工程材料、可选布局与控件约束 | 任务、交付路径、必选与偏好、取证目标 |
| 领域＋共享语义 | 任务、原生记录、版本及来源 | ObjectRef、关系两端与方向、适用范围、证据或未知原因。无需跨域的对象沿用原局部契约 |
| 呈现设计 | 问题、对象及上下文、经过检查的关系和证据 | 定位与核查目标、待比较维度及单位／窗口／基准、缺失处理、完成判据。需要操作时记录意图、发起上下文和结果更新条件。组件名在实现绑定中出现 |
| 界面与资产 | 调用约束、呈现契约、数据与实际支持的入口 | 挂载结果、必要状态和交互绑定、未满足的约束。表现层不补造领域事实 |
| Action / Result | 动作及发起 ID、Case／ObjectRef／配置／Revision，适用时附 Run、参数、证据及授权 | 分开记录执行状态和 Evidence／Finding，按发起记录归档；核对版本与范围后才允许更新。失败保留原判断，不匹配结果留档且禁止写入 |
| 按任务验收 | 调用约束、呈现契约、交付物与证据 | 按路径给出验收和未验证项，分别记录数据、脚本、真实视觉、真实运行 |

呈现模式示例及最小验收：Explanation 能按机制或步骤说明关键关系及条件；Exploration 能在层级中定位对象、查看引用和返回；Comparison 能按共同基准对齐并解释不可比项；Investigation 能跨视图定位、核查、交接并核对结果。模式复用同一领域模型和证据。直接回答可停在领域阶段。

## Workflow 与接口交接

| 阶段 | 执行要求 |
|---|---|
| 识别任务与交付目标 | 用户提交问题、代码、已有产物和可选界面要求，由显式调用或宿主匹配启动。记录布局、Pattern、轴和组件的必选、偏好或由 Skill 决定 |
| 建立领域模型与证据 | 可参考完整 Pattern 识别数据需求。按缺口调用适用的 CANNBot 等工具，并将结果关联到对象。结论与来源足够时直接答复 |
| 定义呈现契约 | 结构呈现／对照与交互调查都明确定位对象和核查依据。调查额外定义发起上下文和结果更新条件 |
| 选择并实现界面 | 必读调用约束和呈现契约。匹配真实支持的布局、Pattern、组件和数据。必选项无法满足或必要证据无法获取时交付阶段性结果、缺口和恢复条件 |
| 按任务验收 | 同时验收约束是否兑现与代表任务是否走通。领域证据、呈现契约、界面实现的问题分别回退。正确显示未知和本轮必要证据齐备分别判断 |

交互工具可由宿主接入 Runtime，静态页面可用同一契约绑定证据并明确标记预设回放。真实事件传输、操作回传和重试留在具体接入说明。共享布局、计算图、泳道、核查面板、缩放和播放的实现另见 [可控 Pattern 接口实施计划](ai-infra-pattern-interfaces-plan.md)。

## 分阶段实施与验收

| 阶段 | 交付物 | 进入下一阶段的条件 |
|---|---|---|
| 1 · 更新基线 | 规则维护源表、代表任务与资产入口、现有验证的通过与缺口记录 | 逐条区分已实现、案例局部支持和文档提案；固定后续比较的旧产物 |
| 2 · 语义与真实映射一起验证 | 现有契约的小幅修订、一个真实跨层案例、现有脚本上的正反例 | 可追溯映射通过；同名跨版本或越运行范围不会合并；非法端点或悬空引用被识别；无证据的关系不被确认；合法未知可展示。涉时间时拒绝无校准的跨域比较 |
| 3 · 呈现与最小 Pattern | 完善现有呈现契约；一条可调用、可验收的 Pattern 绑定，细节见子计划 | 同一领域模型走两种模式，同一交付方式可在两个领域复用；四模式各有最小验收记录；至少一个 Pattern 消费已校验数据，并用实际挂载和操作验证其能力。如未过，先重审职责边界 |
| 4 · 迁移 Skill 职责 | 内容归属、兼容入口、调用回归记录 | 代表任务无能力退化。旧机制讲解仍能渐进阅读和离线交付，调查规则、Glyph renderer 与既有 Style Guide、Tokens、Liquid Glass 均保留 |
| 5 · 调查结果归属 | sync-1 四种回放结果及发起后切换选择、配置与版本冲突的测试 | 有证据则追加结论，证据不足保留未知，失败保留原判断，错上下文留档且不写结论。整个链路沿发起对象归档 |
| 6 · 集成与分发 | 仓库构建、目录及离线包验证，覆盖范围记录 | 从 checkout 与解包后的独立入口验证所需引用可达、分发内容与维护源一致。按规定核对实际浏览器，真实 Runtime 若本期未接入单列 |

顺序采纳“用实际输入输出先验证职责，再迁移 Skill”。第 2 阶段不先造普适 Validator，规则和案例同步确定；第 3 阶段的调查模式可使用已有回放先跑通定位与交接，第 5 阶段再补结果归属不变量。没有真实配对时继续找可溯源案例，固定样本只能验校验逻辑。

## 兼容迁移

先保留六个现有调用名、离线路径、版本和正式资产入口。把规则迁到唯一维护源并通过引用或兼容路由接入，旧正文和新正文不并行维护。核对旧调用的默认交付、交互和边界配置；完成等价验证后再决定入口或目录命名。构建需确认单包与组合包的引用策略，安装副本另行验证。原型、生成页和对外能声明的能力分别记录。

## 延后事项与启用条件

- **通用 Registry、Adapter／插件与 Runtime 平台。** 当前已有局部模型、catalog 和宿主能力。出现多个真实生产者与消费者的重复接入后，再评估共享实现。
- **全面 Schema、复杂校验和独立目录。** 当前先校验首例所用字段与跨记录约束。机器消费、跨模块交换或现有脚本无法表达的要求出现时，再提取最小结构。
- **全量 Pattern 注册、播放和 UI 组件框架。** 先验证一个既有 Pattern 的实际入口，再用第二消费者决定接口边界。有真实步骤或时间输入才扩播放能力。
- **真实 Runtime、授权平台和重试基础设施。** 本期只定义动作、证据归属与更新规则，用回放验证。真实接入由明确的宿主需求触发。

基线见 [总 Workflow 与 sync-1 案例](workflow-editor.html)、[逐节点核对](workflow-skill-node-audit.md)。本轮从 checkout 的现有修改继续实施，保留兼容入口与已定稿视觉资产。
