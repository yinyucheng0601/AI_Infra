# AI Infra 视觉设计复盘：汇报文案评审与优化建议

我阅读了仓库中的 `launch-slides.html`、`speaker-notes.json`、`ARCHITECTURE-REVIEW.md` 和生成后的 `index.html`，重点检查了六章叙事、讲稿、三个案例与最后的设计体系总结。

## 一、总体评价：案例讲得清楚，但设计体系的论证还不够强

目前的汇报更像一场“Agent 时代计算可观测性的 UX 设计复盘”，还没有充分体现你想建立的“智能计算领域视觉设计体系”。

这不是案例数量的问题，而是论证的出发点。

目前的主线是：

CURRENT · 现有逻辑

开发者遇到问题

按需展开证据

人工核查

Agent 复用

PROPOSED · 建议强化的论证

智能计算的领域特殊性

跨层对象、多对多映射、动态执行、异构数据

人的认知限制与 Agent 的工程能力

问题聚焦、空间认知、证据处理、动态生成

领域视觉设计原则与方法论

关系优先、对象连续、按需表达、人机协同

案例验证与视觉知识体系沉淀

Swimlane、Layer Stack、Scale、Glyph / Pattern / Framework / Skill

现有版本已经具备后两层，但前两层主要隐含在案例中，尚未形成明确的理论论证。

这会带来一个问题：听众可能认可你做的几个 Prototype，却未必能理解为什么这些实践需要被上升为一套专门的领域视觉设计体系。

## 三、逐章优化建议

### 01｜设计原则：补上领域复杂性与设计原则之间的因果关系

当前开场是从 Agent 开发过程冗长、代码和数据量巨大切入，随后用 Attention Is All You Need 引出注意力的重要性。这个开场有记忆点，但存在逻辑跳跃。

计算可视化的挑战并非仅仅因为信息太多，而在于模型逻辑、计算任务、编译执行与硬件资源之间存在跨层、多对多、动态变化的关系。即使 Agent 已经处理了大量数据，开发者仍需要理解这些关系才能作出判断。

因此建议将开场讲稿改为：

建议替换的开场论述

AI Infra 的复杂性来自多层计算系统之间的关联。从模型结构到算子执行，从 Tensor 的逻辑形状到实际内存布局，从单核流水到集群通信，同一个计算问题往往跨越多个对象、尺度和时间维度。

Agent 已经能够帮助开发者处理代码、编译文件和运行数据，但这并没有消除人理解计算机制的需求。开发者真正需要关注的是：哪里发生了问题，哪些关系值得检查，当前证据支持什么判断，以及如何调整并继续任务。

因此，我们提出三个体验原则：问题驱动、认知减负、有效控制。让复杂的信息处理交给 Agent，让关键的计算关系和判断依据被准确呈现。

同时，我建议将“问题 / 结果驱动”统一为“问题驱动”，因为结果只是问题的一个入口。设计同样可能从模型结构理解、算法探索、性能预算等任务开始，而不是都需要先出现异常。

“有效控制”则建议在说明中明确为“人对关键决策点的可控性”，避免听众误解为一般的控件交互。

### 02｜Swimlane：从展示异常提升到解释时间关系

现有案例很扎实，尤其是明确了 Host 事件和 Device Trace 的证据边界。讲稿中的 16 条泳道、Lane 6、54 步统计也提供了具体分析过程。

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

GitHub



但目前的文字更像在描述一次调查过程，没有充分解释为什么需要采用泳道和共享时间轴。

建议新增一个核心论点：

计算系统的性能不是多个耗时指标的简单相加，而取决于计算、通信、同步与等待之间的时序关系。

这个判断可以直接解释为什么普通统计图不足以支持某些分析，为什么共享时间轴能让并行关系、阶段衔接和关键等待变得可观察。

建议修改章节导语为：

> 单个耗时指标可以描述性能结果，却难以解释并行任务之间的执行关系。通过共享时间轴，将不同 Lane 的执行阶段、进入时刻和等待关系放在同一时空参照下，开发者可以从整体差异逐步定位到需要核查的事件。

这里要保留 Host 调用窗口的限定。当前案例应当强调“时序关系的表达方法”，而不是宣称已经可视化了完整的计算和通信过程。

### 03｜Layer Stack：从对象连续提升到跨尺度认知

这是我认为最能代表你独特设计能力的一章。

现有讲稿强调 L18 → Query → 64×64 Sample 的连续调查路径，这是正确的。但它的核心价值可以再抽象一层：面对多尺度计算知识，人的理解依赖稳定的空间参照和对象身份。

建议用下面的文字替换章节导语：

> 智能计算对象同时存在于模型、层、算子和数据等多个观察尺度。不同尺度需要不同的视觉表达，但不应该割裂同一个对象的身份与上下文。通过渐进披露和空间参照保持，开发者可以从模型结构进入局部计算与数据细节，而无需在不同视图中重新建立对象关系。

这里建议不要只强调 Zoom，而是强调 Semantic Zoom（语义层级变化）。普通缩放只是把对象放大，语义缩放则可以随着观察尺度变化，改变可见对象、关系及信息密度。

同时，“Object Continuity”应明确包含三件事：对象身份连续、关系上下文连续、证据引用连续。

### 04｜Scale：突出人机协同中的计算可验证性

现有 Scale 案例展示了一个很好的设计机制：开发者修改共享参数，界面根据公式联动输出，并把参数、配置和计算依据保留下来。

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

GitHub



但“改条件，查影响”作为汇报标题显得过于具体，难以体现其方法论价值。

建议明确提出：

领域交互的价值在于把用户操作映射到真实的计算语义，让参数变化及其影响范围可以被理解和核查。

建议章节导语：

> 在计算开发中，用户操作的对象可能是参数、Shape、Layout、并行策略或编译配置。视觉交互需要体现这些对象之间的计算依赖，使开发者能够识别影响范围、比较变化结果，并保留可复查的计算依据。Agent 负责处理数据与执行任务，人负责在关键节点验证假设和调整条件。

这样 Scale 就从一个简单的交互演示变成了人机协同计算检查的一个代表性实例。

此外，当前原型展示的是参考计算和上下文准备，而不是完整 Agent 自动恢复。因此讲稿中应区分“已经实现的参数联动”与“后续目标中的 Agent 自动接收反馈”。

### 05｜设计体系：建议成为整场汇报的理论核心

这一章目前用 Glyph、Pattern、Framework、Skill 四层来解释设计资产如何约束 Agent 输出，方向正确。

但目前仍比较偏“我们有哪些设计资产”。

应当转变为“智能计算视觉知识如何被结构化、复用和执行”。

建议明确四层的职责：

| 层次        | 建议定义                | 设计价值                                 |
| --------- | ------------------- | ------------------------------------ |
| Glyph     | 领域对象的视觉语义单元         | 让 Tensor、Operator、Memory 等对象拥有稳定视觉身份 |
| Pattern   | 领域计算关系的表达模式         | 为数据流、时序、拓扑、内存等关系匹配合适的图形              |
| Framework | 多尺度、多视图的交互组织机制      | 保证对象连续、上下文继承和证据检查                    |
| Skill     | 面向 Agent 的设计决策与验证规则 | 将问题、证据、视觉模式和检查过程组织为可执行工作流            |

还应补充一个重要概念：Domain Schema / Relationship Schema 是这四层资产共同依赖的语义基础。

否则听众可能认为只要规定图元和组件，就能够形成智能计算视觉语言，而跨层对象映射、计算依赖、数据生命周期等最重要的领域关系仍然没有被清楚定义。

建议本章核心表述改为：

> 传统设计系统主要复用界面组件和视觉样式。面对智能计算领域，我们需要进一步复用对象语义、计算关系、视觉表达模式及其交互规则，使 Agent 能够根据工程问题和数据结构选择合适的表达，并检查生成结果是否符合领域约束。
>
> Glyph 定义对象如何被识别，Pattern 定义关系如何被表达，Framework 定义不同视图如何协同，Skill 则把这些规则转化为 Agent 可以遵循的生成与验证流程。

这比“把设计资产变成 Agent 的输出约束”更完整，也更适合用于设计体系汇报。

### 06｜总结：不要让“最少可视化”成为唯一结论

当前最后一章反复强调“生成最少但足够的可视化”。这是一条有价值的体验原则，但它不能充分概括整个领域设计体系。

[image](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com\&sz=32)

GitHub



因为 AI Infra 的视觉需求有时恰恰需要展示复杂关系。例如，多 Rank 通信拓扑或跨层 Tensor 生命周期追踪，过度简化反而会破坏用户对计算机制的理解。

真正的目标应该是：用与判断任务相匹配的视觉复杂度，准确表达计算结构、关系和证据。

因此我建议将结语修改为：

> 智能计算视觉设计的目标，不是生成更多图表，也不是一味减少界面信息，而是根据领域知识、计算机制与人的认知任务，选择恰当的视觉表达。
>
> 通过领域对象和关系的标准化、跨尺度的视觉组织，以及 Agent 驱动的生成与验证，我们希望将分散的计算知识和工程数据，转化为人可以理解、分析和干预的视觉工作空间。
>
> 最终，让视觉设计从一次性的图形交付，走向可复用、可组合、可验证的领域知识体系。

## 四、还需要强化的四项关键论证

这部分是结合上一轮理论讨论后，我认为现有汇报中最明显的缺口。

| 论证维度        | 当前覆盖                       | 建议补充的观点                              | 优先级 |
| ----------- | -------------------------- | ------------------------------------ | --- |
| 跨层知识复杂度     | Layer Stack 涉及多尺度          | 模型、算子、编译、执行、硬件之间的多对多映射，是领域视觉语言的基础    | P0  |
| 静态与动态数据     | 分别有 Layer Stack 和 Swimlane | 静态结构解释计算约束，动态数据呈现实际行为，两者需要关联         | P0  |
| 人的视知觉机制     | 提到了认知减负                    | 明确空间参照、视觉分组、信息密度、语义缩放等设计依据           | P1  |
| Agent 与渲染机制 | 主要讨论 Skill                 | 区分 Agent 的语义编排能力与 SVG、Canvas 等渲染层的职责 | P1  |

尤其是 静态与动态数据之间的关系，值得用一句明确的论点串联第二、三章：

> 智能计算中的模型结构、算子定义、编译配置和硬件拓扑构成相对稳定的计算约束，而 Tensor 数据、执行事件、资源占用和通信行为则随任务运行动态变化。领域视觉设计需要建立静态计算结构与动态运行证据之间的映射，才能帮助开发者从运行现象回到计算机制。

这样 Swimlane 和 Layer Stack 就不再是两个并列的可视化案例，而是同一套设计体系中针对不同数据特征的表达实践。

## 五、文字表达本身，还有三个值得统一的地方

### 1. 减少抽象词的重复，增加明确的设计判断

现有讲稿频繁使用“核查”“证据”“上下文”“判断”等概念。虽然术语一致，但有些句子的信息增量不大。

例如：

原文：

> 判断困难决定证据如何展开。只有摘要不足以说明差异关系时，才选择时间线等表达；同时保留整体参照，突出当前问题。

建议：

> 当开发者需要理解并发、阶段衔接或等待关系时，共享时间轴比孤立的耗时统计更适合表达这些差异。通过保持全局参照并突出相关事件，减少用户在多个指标之间重建执行关系的成本。

后者说清楚了什么时候使用、为什么使用，以及解决了什么认知问题。

### 2. 避免把实现边界写成每页的中心论点

当前版本对证据边界十分谨慎，这是优点。例如明确了 64×64 原型采样不是完整 Tensor，也不是设备观测。

但讲稿中多次出现“不能证明”“不代表”“尚未接通”，容易让汇报听起来过度防守。

建议把这类信息集中在每章的 Evidence Boundary 中，口头汇报优先讲已经实现的设计机制。

例如：

> 当前案例建立了从模型层到 Query 节点及采样数据的连续调查路径。这里验证的是跨尺度对象身份和上下文保持的设计机制。

随后在证据边界中写明采样覆盖范围即可。

这样准确性没有损失，但结论更有力量。

### 3. 让标题承担观点，而不是描述操作步骤

建议统一采用“设计判断 + 解决的领域问题”的标题逻辑。

例如：

- “从总耗时追到待核查的事件” → “以共享时间轴解释并行执行关系”
- “在模型层级间保持对象连续” → “以对象连续性连接多尺度计算知识”
- “改条件，查影响，带着证据交回 Agent” → “以可计算交互支持人机协同验证”

三个标题就能够形成一致的设计方法：时序关系表达、跨尺度对象连续、可计算交互验证。

## 六、建议增加一页真正的理论总览

目前的六章结构可以保留，但我建议在第一章三原则之后，增加一个简洁的理论过渡画面，说明设计原则是从什么约束中推导出来的。

## 为什么智能计算需要专门的视觉设计体系？

领域知识约束

多对象、跨层映射、静态与动态数据共存

计算机制约束

计算、通信、同步、存储与并行关系复杂

人的认知约束

注意力有限，需要空间参照与渐进披露

Agent 工程条件

可自动处理数据、组织关系与生成可交互界面

领域视觉设计的核心任务

准确表达计算语义，降低跨层认知成本，支持人机协同分析与验证。

有了这页，后面的三个案例就可以分别证明不同的设计机制，最后再收敛到 Glyph、Pattern、Framework 和 Skill。
