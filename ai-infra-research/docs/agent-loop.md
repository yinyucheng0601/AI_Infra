AI Agent 的 Loop 设计模式 执行机制与厂商实践
让 AI 修复一个程序问题，通常不会在第一次回答后结束。它需要阅读项目、找到报错、提出修改、运行检查，再根据失败信息调整。真正影响交付的，是这些步骤能否连续衔接，以及系统能否判断什么时候应该换一种方法、请求帮助或结束。
Loop 将模型决策、实际行动和执行反馈组织成持续推进任务的过程。理解它，需要同时看三个层次：设计模式决定任务怎样组织，执行机制决定下一轮怎样发生，运行保障决定状态、权限和退出怎样管理。一个产品可以同时采用多种模式与机制。
本文先拆解这三个层次，再比较 OpenAI、Anthropic、Google、Microsoft 和阿里的公开实现，并以 LangGraph 作为框架参照。厂商部分分析具体 SDK、框架及公开源码，不将某个 SDK 的机制推断为同厂商所有产品的内部架构。文中的八种执行机制是用于理解实现的归纳，并非统一行业标准。
一 从一次回答到持续完成任务
假设项目中的 CSV 导出功能遇到问题：字段中出现逗号和换行时，导出的列错位；空值变成了字符串；交付还要求文件包含 UTF-8 BOM。一个有用的执行过程应当先确认问题，再修改，最后检查数据能否正确解析、字节格式是否符合要求。如果只生成一份看起来合理的修复建议，任务仍然没有完成。
最小的 Agent Loop 可以写成：读取目标与状态，决定行动，执行动作，获取反馈，更新状态，再判断继续或结束。这里的状态包括已经读过的文件、尝试过的方法、当前结果，以及尚未解决的问题。缺少这些信息，下一轮很容易重复上一轮。

模型与运行系统分别做什么
模型负责根据输入生成判断、工具请求或答案。
运行系统负责检查输出、执行工具、追加结果、切换 Agent 和管理限制。
执行环境则真正完成文件读取、网络访问、计算或修改，并返回观察结果。
这种分工解释了为什么工具能力、状态设计和验证方法会明显影响同一个模型的任务表现。
OpenAI Agents SDK 的 Runner 文档直接描述了这种循环：调用当前 Agent 的模型；遇到工具调用就执行并写回结果；遇到交接就切换当前 Agent；得到符合最终输出规则的结果则返回。[1] 运行逻辑由系统执行，模型的输出为系统提供下一步信号。
有三种情况尤其容易误判：
第一，工具没有报错，只能说明某个动作执行成功，不能证明任务已经完成。
第二，模型不再请求工具，可能只是给出了答案，仍需要业务验收。
第三，运行因为次数或输出限制而停止，也不意味着交付合格。完成标准必须独立于技术上的停止信号。
对话历史、任务状态和长期记忆也应区分。历史记录发生过什么，任务状态表示现在推进到哪里，长期记忆保存可能跨任务复用的信息。更新这些内容并不等于训练模型或改变其参数。
二 五种设计模式决定任务怎样组织
设计模式描述完成任务的组织方法。其中反馈驱动、计划驱动和流程约束主要涉及执行组织，验证修复涉及质量控制，多 Agent 涉及协作组织。它们可以组合，不适合用来给厂商贴互斥标签。
反馈驱动 根据当前结果逐步行动
系统不必一开始就知道完整路径，而是在每次观察之后决定下一步。排查报错时，先读日志，随后根据错误位置读取文件，就是这种组织方式。ReAct 风格的推理与行动交替可以帮助理解它，但不能把所有工具循环都直接视为相同实现。
它适合信息不完整、环境变化较大的任务，优势是灵活、启动成本低。代价是局部决策可能缺少全局约束：搜索相同关键词、反复读取同一文件，都可能让系统看起来忙碌，却没有增加有效信息。设计重点是保留尝试记录，并要求每轮行动解决明确的不确定性。
计划驱动 用显式计划维护整体进度
系统先把目标拆成阶段或子任务，再根据执行结果更新计划。修复问题可以拆成复现、定位、修改和验证，某一步失败后，系统需要判断是继续局部修复，还是重新检查原因假设。
这种模式有利于长任务的进度展示、依赖管理与中断恢复。它的成本是计划本身可能错误，维护过细的计划又会消耗时间和上下文。有效设计需要重规划条件，例如关键假设被证伪、连续尝试无进展，或剩余预算已经不足以完成原计划。列出待办事项本身，不代表计划已经参与运行控制。
流程约束 用明确规则规定合法路径
系统预先规定节点、分支和执行边界，模型在允许的位置进行判断或生成。比如必须先完成格式检查，检查通过才能进入交付，失败则回到修复节点。审批、客服和数据加工经常适合这种模式。
优势是路径清楚、便于审计，权限和成本较容易控制。局限是未知情况可能不在分支覆盖范围内，流程越复杂，维护成本越高。实际设计可以固定关键约束，同时允许某个节点内部运行灵活的工具循环。
验证修复 以质量标准推动迭代
生成或执行之后，系统用测试、规则、外部证据或评价结果检查产出，发现问题后修改并再检查。代码修复具有明确测试时，这种模式特别有用。
它的上限受到验证器质量约束。模型自评可能复现生成时的错误；测试也只能覆盖实际写入的要求；针对单个指标的反复优化可能伤害其他目标。因此应区分确定性规则、环境反馈、外部证据与模型评价，并为关键修改增加回归检查。
多 Agent 协作 组织分工与结果整合
当工作可以分成相对独立的部分时，可以让不同 Agent 配置不同工具、上下文与职责。例如一个分析问题原因，另一个检查影响范围，再由主 Agent 汇总。协作既包含个体内部循环，也包含分配、协调和整合的团队循环。
其收益来自合理分工和部分并行，代价包括通信、调度、重复工作和结论冲突。增加角色不会自动提高质量。拆分之前应先判断：输入输出能否说清，子任务是否足够独立，整合成本是否低于拆分带来的收益。

三 八种执行机制决定下一轮怎样发生
同一种设计模式可以用不同机制实现。例如验证修复既可以通过固定迭代，也可以通过图的条件回边，或者通过普通程序循环实现。以下分类关注控制信号和运行语义，机制之间存在重叠与嵌套。
Tool Calling Loop 工具结果驱动下一轮
执行路径是模型生成结构化工具请求，系统校验与执行工具，把返回结果写入输入，再调用模型。工具名称、参数、调用标识和结果需要正确对应，否则模型可能得到不完整甚至错位的反馈。
OpenAI Runner 明确执行工具、追加结果并重新进入循环；Qwen-Agent 的 FnCallAgent 源码同样维护显式循环，检测工具请求、执行工具，再追加 FUNCTION 消息。[1][12] Anthropic Tool Runner 则根据 stop_reason 将响应映射到执行工具、继续请求或停止。[4]
这种机制容易扩展搜索、文件和计算能力，适合探索性任务。缺点是工具结果不断累积，模型可能重复调用，运行成本也难提前确定。通常需要限制轮数、截取相关结果，并记录每次调用带来了什么新信息。各框架对于工具结果后是否再次调用模型可以有配置差异，不能假定所有实现都完全一致。
Handoff Loop 交接后切换当前 Agent
执行路径是 Agent A 请求转交，运行系统切换当前活动 Agent，再由 Agent B 使用自己的指令与工具继续执行。OpenAI 将 Handoff 暴露为模型可调用的工具，例如 transfer_to_refund_agent；AutoGen Swarm 根据最近的 HandoffMessage 决定接管者。[2][8]
其核心是控制权转移。它适合分诊、客服转接和专业责任交接。接收方看到哪些历史，应通过明确的传递与过滤策略决定；交接并不意味着所有本地对象、产物和隐藏状态都会自动转移。
主要风险是来回转交、重复处理或接收方缺少必要信息。应设置合法目的地、交接说明和运行限制。一次交接本身未必形成循环，连续交接与后续执行才构成这里讨论的运行过程。
Agent as Tool Loop 子任务返回主 Agent
执行路径是主 Agent 调用专家，专家完成有边界的子任务并返回结果，随后主 Agent 继续决策。OpenAI Agent.as_tool() 就支持这种组合方式。[3] 专家内部可以运行自己的工具循环，主任务与子任务形成嵌套。

图2 工具调用把结果返回当前 Agent。Handoff 切换活动 Agent。Agent as Tool 在专家执行后将结果交回主 Agent。
与 Handoff 相比，这种方式保留主 Agent 对任务和最终答案的控制，适合统一整合多个专家结果。代价是主 Agent 可能成为瓶颈，嵌套调用增加延迟，专家输出也可能过长或缺少关键证据。需要定义子任务边界、结果格式和失败返回方式，而不只是给专家起一个角色名称。
Conditional Graph Loop 条件边决定下一节点
图结构把工作拆为节点，节点读取状态并返回更新，路由函数根据状态选择后续节点。当路径回到前序节点时，形成循环。LangGraph 的 add_conditional_edges() 可路由到节点或 END，Command 可以结合状态更新与转移；Google ADK 图式工作流也显式定义节点、边和路由。[5][7]
典型例子是生成、检查、修复三个节点：合格则结束，不合格则返回修复。节点内部可以调用模型，也可以只运行普通代码。流程路径由代码明确，不表示所有节点产出都具有确定性。
图片
图3 同一验证结果可以路由到交付、局部修复、重新规划或人工处理。回边负责形成迭代，退出规则负责防止无效重复。
优势是路径清楚、便于观察和测试。代价是复杂分支、共享状态合并与并发更新需要设计。对于 LangGraph，recursion_limit 控制的是 super-step 数量，不应简单当成模型调用次数。条件图还要处理未覆盖状态和无进展回路，画出一张图并不能保证流程会收敛。
Explicit Iteration Loop 固定重复一组步骤
Google ADK 的 LoopAgent 按顺序运行子 Agent，随后重复这一组步骤。循环控制由框架负责，内部子 Agent 可以使用模型。max_iterations 或子 Agent 发出的退出信号用于限制执行。[6]
这适合固定的检查与修改流程，结构容易理解、实现成本低。其局限是顺序相对固定，可能重复已经没有必要的步骤。提示词里写“达到要求就停止”还不够，运行系统需要收到并识别实际退出信号。
Google 当前文档同时提供图式与动态工作流。文章讨论 LoopAgent，是因为它直观地展示了显式迭代机制，而不意味着所有新任务都应优先采用这一模板。
Speaker Selection Loop 调度器选择下一位执行者
AutoGen SelectorGroupChat 的过程是查看团队上下文，选择下一位发言 Agent，执行并广播响应，再检查终止条件。选择可以由模型完成，也可以用自定义函数覆盖。[9]
与 Handoff 的差别在于选择者：Handoff 通常由当前 Agent 提出交接，Speaker Selection 由团队调度器确定下一位参与者。它适合动态讨论和多角色协作，但每次调度会带来额外成本，共享历史也可能迅速膨胀。应定义参与者职责、必要发言顺序和结束条件，避免把团队对话次数误当成任务进展。
Ledger driven Nested Loop 区分推进与重规划
Magentic-One 通过 Orchestrator 维护两类账本。Task Ledger 保存任务事实、假设和计划，Progress Ledger 检查完成情况、进展和下一步安排。内层循环更新进度并分配子任务，持续停滞时触发外层更新计划。[10][11]
图片
图4 内层决定当前计划怎样推进，外层在停滞或关键假设变化时调整整体计划。
它把局部执行与改变整体策略分开，适合需要多步骤与恢复能力的长任务。代价是协调者、账本更新和进度判断都会消耗资源，而且错误的判断可能触发无效重规划。账本不是可靠性的证明，它只是让计划和进度进入可管理的状态。
Programmatic Workflow Loop 原生程序表达控制逻辑
开发者使用条件、循环、函数、并行和递归组织执行，由工作流运行系统记录步骤、处理检查点与恢复。Google ADK Dynamic Workflows 支持这种方式；Microsoft Agent Framework 也提供函数式和图式工作流，当前文档将 Python 函数式 API 标为实验性能力。[7][13]
这种机制适合复杂业务和既有代码集成，表达能力较强。代价是流程不如图直观，开发者需要管理重试、状态和副作用。普通 while 循环可以表达重复执行，但只有结合步骤记录、恢复语义和运行约束，才能支持可靠的长任务。

四 运行保障让循环能够持续且可控
状态管理避免每轮从头开始
完整历史和当前状态应该分开管理。历史可以保留细节供追溯，当前状态则应集中记录目标、已完成事项、待解决问题、关键证据与失败尝试。对于很长的工具输出，保留产物位置和相关摘要通常比无差别塞入上下文更有用，但摘要不能丢掉约束和证据来源。
暂停恢复需要明确重新执行的边界
LangGraph 通过 checkpointer（存档器）、thread_id（存档槽位号）、interrupt() （暂停键）和 Command(resume=...) （继续游戏）支持保存状态、等待输入和恢复。[14] 这类能力可以叠加到工具循环、条件图和协作循环中，不必另立一种任务模式。
恢复时，节点中的部分代码可能再次执行。发送邮件、扣款或写入外部系统等动作，应该使用可识别的操作记录、幂等标识或独立步骤避免重复。Google 动态工作流对已完成子节点的恢复处理也依赖其检查点与节点执行语义，不能简单理解为从任意一行代码继续。
并行分发与汇总不一定构成循环
Fan-out 将独立任务分发，Fan-in 汇总结果。一次分发和汇总可以是无环流程，只有汇总发现缺口并再次分发，才形成迭代。并行适合互不依赖的工作，也会引入状态合并、部分失败和资源竞争。不要并行修改同一份无法安全合并的状态。
将权限与人工输入放在具体节点
有些行动需要执行前批准，有些任务缺少必要信息，还有些产出需要人工复核。这些情况应分别表现为批准节点、补充信息节点或审核节点。用户是否同意行动，与系统是否具备实际访问权限也是两件事。

五 一个完整案例 CSV 导出修复如何形成闭环
任务与验收条件
我们构造一个可复现的 CSV 导出器：输入是若干记录和指定列顺序，输出是 UTF-8 CSV 字节。验收要求包括普通文本、中文、数字、缺失字段、列顺序、空数据表头，以及包含逗号、引号、换行和回车换行的字段。空值应导出为空单元格，文件还要包含 UTF-8 BOM 字节标记。
案例使用 Python 标准库 csv.reader 对导出结果进行回读，并检查预期单元格；BOM 由字节断言验证。共 12 个具名检查。执行脚本和原始结果随文档配套保存，运行 run_case.py 可复现数据。[15]
实验使用固定修复步骤与条件路由，真实执行导出和验证，没有调用大模型。因此它展示的是反馈、状态和退出的运行机制，不能用于衡量 Agent 的自主修复率、模型推理能力或真实项目表现。
初始实现与第一轮反馈
初始版本直接用逗号拼接字段和用换行拼接记录。普通内容看似正常，但它不处理 CSV 转义，None 被 str() 转成文本，文件也没有 BOM。
第一次检查得到 6 项通过、6 项失败。失败集中在含逗号、含引号和逗号、含换行、空值、含回车换行和 BOM 六类。这些结果将模糊的“导出有问题”转成可定位的失败集合。
第一次修复与回归检查
第一次修复改用 csv.writer，并采用 CRLF 记录结束符。它解决特殊字段的引号与转义，并按标准库行为将 None 写为空单元格。随后重新运行全部 12 项检查，而不是只检查刚修改的情况。
结果为 11 项通过、1 项失败。剩余问题是 BOM 字节要求。此时系统应该保留已经通过的结果，同时将未解决状态缩小到编码标记，而不是再次修改 CSV 引号规则。
第二次修复与结束判断
第二次修复在输出前加上 UTF-8 BOM 字节，重新运行全部检查。最终 12 项全部通过，路由从 REPAIR 变成 END。它代表满足本实验的验收条件，不代表已经覆盖所有数据规模、Excel 版本或应用导入行为。

六 各家厂商如何分配执行控制权
比较厂商时，应该先看具体产品或框架，再看控制权放在哪里。SDK 支持某种机制，不意味着该厂商的闭源产品默认采用完全相同的执行路径。
OpenAI 在 Runner 内连接工具调用与交接
Agents SDK 的 Runner 根据模型结果组织后续行动：工具调用进入执行与结果回写，Handoff 切换当前 Agent，最终输出触发返回。[1][2] 通过 Agent.as_tool()，主 Agent 还可以保留控制权并调用专家。[3]
它为开发者提供了直接的控制流原语。设计重点在于明确哪些工作应调用后返回，哪些工作需要转移负责人，以及上下文如何传递。优势是组合直接，代价是业务级计划、验证和异常处理仍需要明确设计。这里的公开 SDK 行为，不能直接证明 Codex 完整内部架构。
控制流原语的意思是：
OpenAI 的 SDK 很 "底层"—— 它只给你最基础的三块积木，至于你要搭成 "先做计划再执行" 还是 "先验证再修复"，全靠你自己设计。
好处是灵活，想怎么组合都行；代价是你得自己想清楚：
哪些活儿是 "调个工具就完事" 的

哪些活儿是 "必须换人负责" 的

换人的时候哪些上下文要带过去

一句话总结：控制流原语 = SDK 给你的最基础流程积木（工具调用、交接、专家调用），你拿这些积木自己搭出完整的 Agent 工作流。

Anthropic 根据停止原因区分执行 继续与结束
本轮核实的 Tool Runner 源码将 stop_reason 映射到 run_tools、resume 和 stop。tool_use 触发执行客户端工具并追加结果；pause_turn 与 compaction 等状态触发继续请求；end_turn、max_tokens、refusal 等状态走停止分支。[4]
这个实现说明“继续”并不总是因为工具调用，也可能是服务端任务尚未结束。它也说明停止状态的业务意义不同：自然结束、输出上限和拒绝不能被统一显示成“任务完成”。优势是运行信号明确，业务系统仍需要将其转换为合适的交付状态。该分析对象是 SDK Tool Runner，不是对 Claude Code 全部内部机制的推断。
Google 提供固定迭代 图与动态控制三种表达
ADK 的 LoopAgent 展示固定子步骤迭代；当前文档还提供图式工作流，通过节点和路由明确流程；动态工作流则用程序语言组织条件、循环和递归，并记录子节点执行。[6][7]
这些方式的区别主要在流程表达位置。结构稳定时可以用模板，分支清楚时可以用图，控制逻辑复杂时可以使用程序式组织。优势是选择范围较广，代价是需要理解各语言、版本与恢复语义的差别，不能仅凭“支持循环”就认定使用体验相同。
Microsoft 从发言调度发展到显式工作流与重规划
AutoGen 的 Swarm、SelectorGroupChat 和 Magentic-One 分别展示交接、团队执行者选择与账本驱动的内外层循环。[8][9][10] 它们解决的问题不同：选择谁执行，不等于判断计划是否仍然有效。
Microsoft Agent Framework 当前将执行器、边、事件和状态纳入工作流运行模型，并提供 Sequential、Concurrent、Handoff、Group Chat 和 Magentic 等编排方式。[13] 优势是能显式组织协作与运行状态，代价是结构、协调逻辑和框架版本的理解成本。AutoGen 论文中的实验成绩也不能直接当作今天 Agent Framework 的性能数据。

定位：长程、开放式、多步骤任务的“总控 + 专家团队”，强调计划管理与可恢复性；是面向通用助理场景的产品化编排，而非通用多 Agent 基础设施。

业务定制要改 Agent 集合与提示词，迁移成本高

阿里 Qwen Agent 展示清晰的工具调用循环
FnCallAgent 源码维护调用预算，在循环中调用模型、识别工具请求、执行工具并写回 FUNCTION 消息；模型没有使用工具时可以退出。[12] 这一实现适合观察最小工具循环需要哪些步骤，也便于开发者定制工具和业务状态。
它的基础机制清楚，但持久化计划、严格验收、人工节点和跨 Agent 协调不能仅凭这一个类推断为已经具备。是否需要扩展，应由任务要求决定。
LangGraph 作为显式状态与图控制的参照
LangGraph 将节点工作、状态更新和路径选择分开，允许条件边、动态路由与并行分发，并结合检查点和中断恢复。[5][14] 它适合需要检查执行路径和恢复任务的场景。
这种结构的价值是让控制逻辑可见，代价是状态模式、合并规则和节点边界需要认真设计。图中的模型节点仍可能生成错误结果，显式流程并不能替代可靠验证。

七 公开评测能告诉我们什么

移除协调组件后的消融结果
论文第5.3节在 GAIA 验证集上开展消融。将 Orchestrator 替换为较简单的 GroupChat 调度后，去掉了账本、计划、进度追踪、循环检测与显式任务指派等机制，作者报告性能相对下降 31%。移除单个工作 Agent，也造成 21% 至 39% 的下降。[11]
这里的 31% 是相对下降，不是下降 31 个百分点；多个组件同时变化，也不能解释成“单独增加账本必然提高 31%”。它支持的结论更具体：在该实验配置和任务集上，只选择谁发言，不能替代完整的进度管理与任务协调。
更复杂的循环也有固定开销
论文作者指出，系统在较长、多步骤任务上的收益可能更明显，而固定协调开销可能给短任务增加出错机会。这是作者提出的解释，不是对所有多 Agent 系统的普遍定律。
WebArena 的自划分验证集完成率为 35.1%（148/422），保留测试集为 30.5%（119/390）。作者将其作为可能存在轻度过拟合的提示。验证与测试的差异说明，即使循环设计看起来合理，也需要在未用于调试的任务上检验。
论文的错误分析还识别出持续无效行动和验证不足等问题。对应到产品设计，就是需要记录失败尝试、检测停滞，并在交付前执行与风险相匹配的检查。该错误分析使用模型辅助归纳日志，不应视为完全独立的人工因果审计。
八 怎样比较 选择并改进 Loop
用五个问题读懂一个实现
第一，谁决定下一步，是模型、程序、图路由还是团队协调者。
第二，什么信号触发继续，是工具请求、交接、检查失败还是进度停滞。
第三，状态存在哪里，怎样传给下一步。
第四，谁验证结果，依据是测试、外部证据还是模型评价。
第五，谁决定结束，怎样区分完成、失败、暂停和预算耗尽。

这五个问题比“是否支持 Agent”更能帮助判断实现差异。它们也适用于阅读开源代码、评估框架和设计产品交互。

不必一开始就引入多 Agent、复杂图和长期记忆。先明确完成标准和有效反馈，再观察失败集中在哪里。只有当现有结构不能管理实际复杂度时，新增计划层、专家分工或持久化机制才有明确收益。
将效果与运行成本一起记录
评估应同时记录任务完成率、验证质量、总耗时、模型与工具调用、无效重复、人工介入和恢复表现。对比不同方案时，要固定任务、起始状态、工具权限、模型配置、预算和验收方法，并进行足够重复。条件不一致时，应呈现差异而不是强行得出排名。
CSV 案例展示了为什么完成率需要结合覆盖范围理解：12 项全通过，是对这 12 项验收的结论。要走向生产，还需要添加更大数据、编码差异、异常输入和实际应用导入验证。真实 Agent 评测则还需要记录模型调用和自主决策，不能用程序化修复的结果替代。
结语 Loop 的价值要由任务进展证明
回到最初的修复任务，模型需要选择行动，工具需要提供真实反馈，状态需要保留进展，验证需要判断结果，运行系统需要处理继续与退出。多种机制围绕这些职责组合起来，才构成可以交付的执行过程。
有效的 Loop 应当让每轮行动有依据，让反馈能够改变决策，让失败推动策略调整，并在达到要求时提供可复核的交付证据。选择哪种机制，最终取决于任务中的不确定性、验证条件和控制要求。
