# 二、从人的视知觉出发：如何让复杂计算变得可理解？

智能计算系统的难点不只是信息量大，而是模型结构、算子依赖、数据布局、硬件资源和运行时行为相互关联。领域视觉设计需要同时回答两个问题：计算关系本身是什么，以及人怎样才能在有限注意力和工作记忆条件下识别、比较并理解这些关系。

视觉系统能够较快地发现某些位置、形状、颜色和运动差异，并依据邻近、相似与共同区域等线索组织对象；但这种感知优势不等于用户能自动理解技术语义。设计的任务，是把计算对象及其关系映射为可辨认、可追踪、可验证的视觉结构，使开发者把认知资源更多地用于分析计算问题，而非反复寻找和拼接信息。

## 1. 从视觉认知机制建立视觉编码规则

结合视觉感知与认知研究，可以归纳出五类对复杂计算可视化尤其有价值的机制。它们是面向设计任务的综合框架，而不是某篇研究提出的标准“五能力模型”。

| 视觉认知机制 | 可利用的感知特点 | AI Infra 设计应用 |
| --- | --- | --- |
| 空间定位与关系判断 | 识别相对位置、顺序与空间关系 | 用有意义的轴线和区域组织 Layer、Rank、Core；保留可追踪的位置参照 |
| 知觉分组 | 依据邻近、相似、连接和共同区域将元素组织为整体 | 用空间邻近、边界和连线表达计算单元、依赖组与硬件分区 |
| 视觉特征检测 | 较快发现形状、方向、颜色等显著差异 | 用有限且一致的编码区分类别、状态及异常，并配合文本或图例解释语义 |
| 运动与变化感知 | 注意连续变化、方向和事件转换 | 对 DMA、Token Dispatch 和流水执行提供可暂停、可回放的过程表达 |
| 空间记忆与对象连续性 | 借助稳定参照跟踪对象及其变化 | 在缩放、过滤、切换视图时保持对象锚点与关联线索，减少重新定位 |

知觉分组的研究表明，共同区域等视觉线索会显著影响人如何把图形元素组织成整体[1]。但分组方式必须对应真实的计算关系：视觉上被同一容器包围的对象，不应让用户误以为它们具有实际上不存在的归属关系。

运动能够帮助展示时间关系，但并不必然比静态图更容易理解。对于需要准确比较多个任务耗时的场景，应优先保留可对齐的时间轴；对于需要观察执行先后或数据搬运过程的场景，再采用可控制进度的动画[6]。

**视觉编码的优先级应由用户需要完成的判断任务决定。** Cleveland 和 McGill（1984）的图形感知研究，以及 Heer 和 Bostock（2010）的后续实验，都表明不同视觉编码会影响数量比较的准确度。对于精确数值比较，共同尺度上的位置和对齐长度通常比面积等编码更合适；但这并不意味着面积和三维表达在所有任务中都无效[2][3]。

因此，领域视觉语言需要建立明确的语义契约：

| 视觉属性 | 适合优先表达的语义 | 典型场景与约束 |
| --- | --- | --- |
| 位置、顺序与坐标轴 | 层级、执行次序、定量对齐 | Layer 序列、Core 泳道、Latency 比较；需要说明坐标的含义 |
| 形状与封闭区域 | 对象类别、模块边界和归属 | Tensor、Operator、Memory；容器关系必须对应实际结构 |
| 连接、箭头与线型 | 数据依赖、调用、通信和同步 | Producer–Consumer、Collective、Set/Wait；必要时标明方向与类型 |
| 网格与面积 | 形状、Tile 划分、规模概览 | Shape/Tile 网格、Memory 容量；精确值仍提供刻度或数字 |
| 长度与对齐位置 | 延迟、带宽、占用量等定量比较 | 对齐时间轴、条形标尺；避免用透视长度直接比较 |
| 色相与明度 | 少量类别或具有顺序的状态 | Compute、Memory、Communication；避免同一通道同时承载多种无关语义 |
| 运动与状态转换 | 实际执行过程或变化方向 | Token Dispatch、DMA；支持暂停、单步和关键帧定位 |
| 纹理、描边与透明度 | 次级状态、选择、不可用和重叠 | Sharded、Unmapped、Selected；提供非颜色的辨识线索 |

色彩可以先建立一套候选语义：蓝色对应计算对象，绿色对应数据与存储，紫色对应通信，灰色对应结构与上下文，橙色对应待关注状态，红色对应已确认的异常或故障。但类别与状态是两个不同的语义维度：一个计算节点出现故障时，应优先保留其对象类别，再利用告警描边、图标或局部强调表达故障，避免直接将整类对象改成另一种类别颜色。具体颜色含义应通过跨工具一致性及可辨识性测试确定，而非假设颜色天然具有固定的技术语义。

## 2. 从信息容器转向计算对象与关系的空间组织

传统的标题、卡片、表格、图表与详情页并没有失效。表格仍适合参数查找与精确数值读取，日志列表适合文本检索；但当开发者要回答“某个 Tensor 从哪里产生、经过怎样的转换、最终影响了哪个 Core 的执行”时，孤立的信息容器容易割裂对象之间的因果与结构关系。

因此，智能计算领域更需要以**对象及其关系**组织信息，让计算结构成为用户持续理解的主线。

以一个 Tensor 为例，开发者可能需要连续追踪：它处于哪个模型或算子上下文，由哪个 Operator 产生，Shape、Dtype 与 Layout 如何定义；经过哪些 Tile 化或分片转换，映射到哪些 Rank/Core，驻留于何种内存空间；最后被哪些任务消费，又在运行时产生了怎样的读写、同步或性能变化。

这里不意味着把所有信息一次叠加在同一个画面中，而是建立一条**可追溯的对象关系链**。逻辑 Tensor、编译后的 Tile、跨 Rank 分片和物理内存分配并非始终是同一个实体；它们可能是一对多、多对一或跨版本的转换关系。界面应该保持稳定的对象标识与来源关联，同时明确展示派生、切分、映射和别名等关系，避免用视觉连续性掩盖真实的数据变换。

在交互上，可采用三个相互配合的机制：

1. **稳定空间参照**：在模型层、算子层、Tile/Core 层切换观察尺度时，保留当前对象的位置线索、上级归属和所在路径，降低重新定位成本。
2. **语义缩放与按需展开**：缩小时突出整体结构、分布和异常；放大时逐步呈现 Tensor、Tile、指令和内存细节。缩放改变的是信息分辨率，不能无提示地改变对象含义。
3. **跨视图关联**：从算子图选中 Tensor 时，能够定位其 Tile、内存映射和相关执行任务，并在不同表达之间保留对象身份、选择状态及证据来源。

不同任务可以采用单一画布或多个协同视图，关键是让用户保持对同一计算对象的连续理解，而不是要求所有内容都只能放进一个画布。多视图设计研究也强调，应权衡互补信息的收益与视图切换、学习和注意力分配的成本[4]。

这一设计方向的目标，是让开发者通过视觉空间理解原本需要在多个代码文件、日志、指标和文档之间反复切换才能建立的计算关系，并能够从整体定位问题、追溯证据，再回到具体对象执行验证。

## 3. 用认知负荷管理信息深度与分析路径

认知负荷理论指出，工作记忆处理新信息的能力有限，任务本身的元素关联和信息呈现方式都会影响理解难度[5]。这一理论应用到 AI Infra 时，需要区分三个概念：

| 概念 | 含义 | 计算开发中的例子 |
| --- | --- | --- |
| 内在认知负荷 | 理解任务所需的认知资源，受对象关联程度及用户经验影响 | 理解 MoE 路由、分布式通信及跨核同步 |
| 外在认知负荷 | 由不必要的信息查找、组织与呈现方式额外引入的认知需求 | 在多个页面之间寻找同一个 Tensor 的上下游证据 |
| 有效认知投入 | 用户为形成理解和完成判断而投入的相关认知加工 | 比较 Pass Before/After，解释 Layout 变化为何影响访存 |

其中，“有效认知投入”是为了设计表达而采用的描述，不应误写成与前两类严格并列、毫无争议的第三种系统复杂度。内在难度也并非固定不变：同样的执行泳道，对于熟悉相关硬件的专家和新接触该领域的开发者，认知需求不同。

据此，可以提出三个信息呈现策略。

**第一，按任务分层，而不是仅按技术目录堆叠。** 系统保留可追溯的专业细节，但当前画面优先回答正在进行的分析问题。例如调查延迟异常时，先展示异常 Core、时间差异与关键等待关系，再进入具体指令或内存访问证据。

**第二，渐进披露，但允许专家直接到达目标。** 默认从整体到局部建立上下文，按照模型、算子、Tensor、Tile、Core 与指令等相关尺度逐步展开；同时支持搜索、定位与深度链接，使熟悉目标的开发者可以跳转到所需分析层级，而无需被迫走完整条引导路径。

**第三，关联证据，而不是重复展示对象。** 同一个逻辑对象在计算图、内存视图与执行泳道中，应通过稳定标识及显式映射关系互相定位；不同层级的派生对象则要展示转换依据。用户既能看到结论，也能继续检查它来自哪个 Pass、哪段 IR、哪次执行或哪项指标。

这三个策略最终指向一个可验证的体验目标：**减少无关查找与上下文切换，把有限的认知资源留给真正需要开发者作出判断的计算关系。** 它的效果可以通过定位问题所需时间、跨视图往返次数、对象对应错误率，以及对依赖关系的理解准确度来评估，而不只以界面信息密度或视觉复杂度衡量。
