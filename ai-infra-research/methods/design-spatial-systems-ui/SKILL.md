# Spatial Systems UI

## 资源与职责

先完整阅读 [风格规范](references/style-guide.md)。选择主体形式时阅读 [可视化决策](references/visualization-patterns.md)；评审与交付前阅读 [验收规则](references/review-rubric.md)。实现时复用 [设计变量](assets/design-tokens.css)，映射到现有项目变量，避免全局样式污染。实现深色空间画布悬浮控件时，阅读 [Liquid Glass 接入](references/liquid-glass.md)，复制内置 JS/CSS 到目标项目；使用已确认的小控件、面板分离预设，不重新手写光学效果。

负责呈现，不替代领域知识验证。与 llm-compute-diagrams 等领域 skill 同用时，让领域规则决定对象、结构、箭头和数据含义，让本 skill 决定整页构图与外围界面。保留已有图元的语义规范；不要用小圆角控件规则覆盖算子图元。用户明确要求和项目约束优先，冲突时说明取舍。

## 源码调查视图

当任务是核对索引、分块与搬运布局时，本 Skill 负责开放画布、关联选择和按需检查器，不负责推断 API 或自动诊断。若有领域 Skill，先接收其对象、映射、来源及未确认项；没有领域适配时可呈现已确认的关系，但不要为完成画面补出缺失映射。任务入口与交接层级由 `observability-design-style` 负责；本 Skill 按 [呈现边界](references/investigation-view.md) 检查可读性、命中面积与视角保持。普通编译报错或单项耗时查询不应因为有本 Skill 就强制画图。

## 工作流程

1. 确认范围。区分评审、方案、实现；评审和“先不要执行”只输出分析，不修改文件。读取现有页面、数据和用户视觉参考，不凭文件名或历史描述判断现状。
2. 确定任务。识别主体、用户需要回答的问题、数据维度、当前焦点与必要操作。缺失数据标明未知，演示数据注明模拟，禁止虚构因果和传播。
3. 选择形式。按可视化决策表选取 2D、空间视图或 canvas，不为风格强行增加 3D。定义总览、聚焦、检查、沉浸状态，以及各尺度显示的信息。
4. 建立构图。先安排主体实际可见边界、安全区和视觉重心，再布局身份、状态、图例、操作与导航。用共享对齐线、明显字号跨度和局部密度建立不对称平衡，不平均填满四角。文档面积与字号范围只是起点；时间轴、比较任务和无限画布允许宽幅结构。
5. 建立样式。默认严格中性灰，基础色 R=G=B；白色表示选择、橙红表示异常，并以形状或文字补充。按任务引入其他颜色，不自动加载整个调色板。保持跨视图色标一致，不用透明度改变热力数值制造景深。空间画布区分主体与外围控件：主体保持结构线条和色块，悬浮控件按风格规范第 10 节使用 Liquid Glass：小控件为 control，密集面板为 panel，独立圆按钮为 icon；主体图元保持原有语义材质。按用户要求可用浅色主题，并重新校验对比。
6. 实现交互。信息 Zoom In 优先原地展开，通过连续 Transition 保留对象的空间关系与上下文；具体要求见下方“信息 Zoom In 与连续过渡”。Hover 仅快速预览，点击建立稳定选择，精确数据进入可固定检查器。打开检查器不重新平移或缩放主体，优先避让；无空白时进入沉浸检查并保留返回状态。细导航表达完整范围，分析性时间轴仍保留真实持续时间。支持键盘、触控和减少动态效果。
7. 运行检查。使用环境许可的方式实际渲染，检查目标桌面与窄屏截图，测试总览、选择、检查器开关和缩放状态。不得绕过预览权限或声称未完成的检查通过；受阻时区分代码检查和视觉验证并报告限制。
8. 迭代交付。按验收规则修复遮挡、重心、排版和读数后重新检查，简述变更及未验证项。遵循项目交付方式，不擅自发布网站或替换技术栈。

## 取舍原则

### 核心原则：Let layout explain itself

减少解释性的文字和标签，让布局本身解释结构。优先用位置、对齐、邻近、分组、留白、尺度层级和连接关系表达归属、顺序、依赖与差异；布局尚不清楚时先调整构图，不用更多说明补救。删除重复描述已可见关系的句子、标签和图例，避免同一信息在标题、卡片、图内与说明中反复出现。

保留识别对象所需的名称、关键数值与单位、必要的状态和非显然语义。补充解释按需进入详情或检查器，并保持键盘和触控可达。验收时暂时忽略解释性文字：主体层级、分组、阅读顺序和关键差异仍应清楚；若不清楚，优先修改布局，再补充最少必要标注。

先保证数据和交互正确，其次优化构图和尺度层级，最后精修字体、线条与控件。保持业务功能，不为视觉效果删除分析能力。将大标题用于当前对象，不默认放大产品名称。

将开放舞台与周边信息作为默认模式，不强制同一布局；比较和多面板诊断可保留必要分区。参考图只借鉴构图、抽象与秩序，不复制品牌素材。没有附带截图时依据规范执行，不声称已查看外部作品。

### 信息 Zoom In 与连续过渡

从总览进入更细的信息尺度时，优先在当前对象所在位置展开，延续原有图元、布局锚点与关联关系。避免无必要地跳到独立窗口或重新绘制一张失去上下文的图；独立任务或并排比较确有需要时，可采用分区视图。

将 Transition 作为信息层级之间的连接：让对象的位置、尺度和结构连续变化，使用户看清细节从哪里展开、哪些对象发生变化。避免瞬间替换、突然滚动和无关对象一起运动；返回时恢复先前的视野、滚动位置与选择。遵循减少动态效果偏好，即使弱化动画也应保留清晰的对象对应关系。

## 已定稿页面与诊断修复交互

在已批准 UI 上增量修改，或设计告警、方案选择、修复前后对照时，先读 [增量设计与修复流程](references/approved-ui-and-repair-flow.md)。保留定稿结构；优先填充分组；一项决策用一张完整卡片；用户明确的实心材质优先于默认 Liquid Glass。

## 复用与验收契约

创建或改造有源码证据、多视图联动的可视化时，先读 [可视化交付契约](references/visual-delivery-contract.md)。先落实任务路径、资产版本和代表状态，再展开页面；不要用新增说明面板补救不清楚的布局。已有项目有同等约束时直接复用，不另建重复流程。

配置菜单、工具栏、悬浮面板与提示的具体实现遵循风格规范第 9–10 节，并按验收规则检查当前/悬停/焦点、单一 tooltip、内容适配高度及控件分组；这些状态属于组件契约，不能只按静态外观验收。

## 交互高亮与语义颜色

交互高亮不默认使用绿色。先读取宿主已确认的 selection / highlight token；没有约定时使用中性近白填充与深色文字。绿色仅用于已有明确语义的成功、健康、已排除状态或正式图元的数据角色，不得从示例 OP、Tensor 或绿色状态胶囊推导出全局 accent。选中、关联、hover 与状态色分别定义；保留图元原有语义，不把所有相关对象染绿。
