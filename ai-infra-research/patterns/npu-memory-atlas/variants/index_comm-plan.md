- 保留原有单卡／全部 Rank、2.5D／Top／Front、显存组成／分片、选择、缩放、拖动、播放与设置的交互框架和默认进入方式。
- 通信是现有 Rank 场景中的增量图层。禁止隐藏原 UI、另设全屏容器、把 Rank 改排成单独的一行、增加独立工具栏或第二套播放器。
- 新增通信线继承既有关系线的视觉语言。极简要求只约束新增图元，不能作为重设计既有 UI 的理由。

## 二、纠正上一版方向

上一版使用 `ep-app` 全屏容器和 `ep-active` 隐藏原 UI，新增组选择、读数卡片、独立时钟及视图入口。这改变了已经定稿的界面，是错误实现方向。

后续首先撤掉上一版独立界面的挂载与样式加载，恢复副本的基准界面。恢复前对比基准、副本与本轮新增文件，逐项识别改动，保留用户原有修改；不直接覆盖整个副本，不做全量 Git 回退。此前数据模型仅作为候选逻辑复用，经核对后才能接入；原测试通过不代表方案符合需求。

## 三、通信如何进入现有界面

沿用“全部 Rank → Top”，点击某个 Rank，在已有关系选择器内选择 EP。只在这个 Rank 所属 EP 组的原有位置之间显示通信，不移动卡片，不改变空间坐标含义。EP 选项属于现有选择器的内容扩展，控件外观、位置和显隐规则不变。

首版只聚焦所选 Rank 的发送／接收关系，避免全组连线遮挡。端点复用既有 `rankPosition` 与投影，随原缩放、拖动和配置更新；通信线不能截获 Rank 点击。

复用现有播放、暂停、重置、时间轴和状态文本。路由、Dispatch、专家计算、Combine 是现有模拟时间中的事件，不另起播放器。首次只接入一个明确的 Layer × 微批次事件，与现有模拟前向区间对应；其余时间区间不显示该事件的活动流。时间映射明确为教学假设，不声称复现真实调度。

| 阶段 | 原场景中的增量表现 | 数据含义 |
| --- | --- | --- |
| 路由 | 原 Rank 和 EP 关系可见，尚无活动传输 | 确定目的专家，本地 Token 无跨卡边 |
| Dispatch | 原卡片间显示有向细线，以克制的透明度／线段进度区分活动传输 | Token 激活发往专家所在 Rank |
| 专家计算 | 不显示活动传输，已有状态文本显示计算阶段 | 专家处理收到的 Token |
| Combine | 同一组端点间反向显示返回关系 | 专家输出返回 Token 来源 Rank |

初版不强制使用宽带 Sankey。Top 优先保留原布局和可读性，以有向关系与阶段状态解释分发、回收。后续若采用宽度编码，只能表示一次明确事件的总量，不能称作瞬时流量；选定窗口的聚合 Sankey 不作为实时场景的替代界面。

数据说明使用现有状态文本与图元悬停提示，不新增读数卡片、图例栏或常驻面板。已有承载位置不足时先收缩信息量，不挤压或改造定稿 UI。

## 四、配置与模型边界

继续采用用户认可的 rank-intro 数量基准：TP2、CP1、PP4、DP16、EP8、ETP1，共 128 Rank；48 Layer、64 Expert、H4096、FFN2048、序列8192、MBS1、8 微批次、64 GB HBM。配置复用是数据变化，不是改样式的授权。

- Rank 编号为 `(pp * DP + dp) * TP + tp`；EP 组固定 PP、TP 与 DP 内的 EP 分组。
- ETP1 专家参数副本关系与 EP Token 交换组分别建模，不混用。
- 首版采用标明假设的 Top-1 教学路由。本地 Token 不计网络 payload；跨卡 payload 按 Token 数、hidden size、dtype 字节数计算。
- Dispatch 与 Combine 分别计量，全网流量不重复累计同一次发送和接收。不从教学播放速度推导 GB/s。
- 当前通信缓冲、收到的激活、累计网络字节分别定义。接入原“通信缓冲”类别时替换该事件对应的模拟分量，避免重复累计；无法合理拆分前不显示伪精确联动。
- 不顺带重写全部显存模型、梯度 dtype 或训练调度。只调整 EP 与配置一致性所必需的计算，其余差异明确记录。
- 128 Rank 使用原自动适配与间距配置，不通过改变卡片造型、工具栏或 UI 排布解决数量增加。

### 要讲清楚的完整过程

以选中 Rank23、追踪它的 Token 为例，固定来源身份贯穿各阶段：

| 阶段 | 必须能直接看懂的内容 | 原场景内的表现要求 |
| --- | --- | --- |
| 路由分桶 | Rank23 的 Token 按目的 Rank 分成几份；哪些留在本卡 | 在原 Rank 图元内部表示目的份额，本地部分与跨卡部分可区分；本地 Token 不绘制网络自环 |
| Dispatch 分发 | 哪一份正在发给哪个 Rank，发送进行到哪里 | 原连线有清楚的方向与传输进度；目的 Rank 内同步出现对应的接收量变化 |
| 专家计算 | Token 已到达，正在本地处理，当前没有网络传输 | 保留已接收数据的可见状态，停止活动传输；通过原状态区及必要的图元状态表示计算 |
| Combine 回收 | 专家输出从哪里返回，来源 Rank 收回了多少 | 在同一组端点之间反向传输，来源 Rank 的已回收量随进度增加；不能描述为原始激活原样回流 |
| 完成 | 这一批 Token 对应的结果已返回 | 已回收量达到该事件应返回数量，通信活动结束，暂存按模型释放；本地结果计入完成量但不计跨卡流量 |

图中的接收变化首先表示“来自所选 Rank23 的这一份”，不能将局部追踪量冒充目标 Rank 的全组接收总量。源 Token 数量、目的端已收到数量和来源端已回收数量使用一致的事件范围，并与底层模型对应。

5. 来源 Layer 图中的 `layerMB` 是独立展示数组（L7=246.4），周期账本由 `perMb` 等公式生成；缓存高水位还包含为维持案例余量而作的时间调整。以上是教学构造，不是实测归因。合入时先统一账本，再由它生成各图，不能把静态图数值直接加进已有显存。
6. 来源 117 MB 按 `117 * 2^20` 计算，本页通信字节显示按十进制 MB。数据一律存 bytes，新增事故图按 MiB/GiB 标注，避免单位混算；246.4 等展示近似值须注明。

### 14.3 分步实施与验收

1. **统一案例数据**：新增独立事故数据模块，定义样本范围、64 专家归属、Rank 分布、微批与层索引、字节单位。验证专家和为 8,192、每组专家和等于所属 Rank、E27=4,505、R23=4,915。明确 UI 第四微批对应内部索引 3。
2. **实现事件账本**：从来源提炼 1F1B／逐层保留与释放所需逻辑，输出 `snapshot(rank,time)` 与失败申请事件。每张图都从同一账本生成。保证前三份 L7 激活尚存、第四微批 L0/L1 已成功、L2 未成功；失败前后已用量不因被拒的 117 MiB 增长。
3. **接入 OOM 证据图与共享播控**：先完成聚合目的分布和四段钻取，再考虑有明确来源矩阵的传输动画。测试切场景、暂停、回拖、重播、退出后恢复普通通信状态。不能用另一个 CSS 动画时钟播放证据。
4. **接入峰值／GAP**：定义 A=算子分配、H=算子持有、R=算子保留、P=进程保留；D=H−A，I=R−H，O=P−R，验证 P=A+D+I+O。P 峰值拆账必须使用同一时刻快照，不能相加各分项独立最大值。持续时间注明阈值；沿用来源时 GAP 高位阈值为 max(1 GiB, 容量×5%)，P 高位为其峰值的 90%。来源以 81 个归一化时间采样估计持续比例与 byte×Step 积分，不包装成精确 byte×秒。池内空闲不直接称为碎片，展示词统一“缓存/预留”。
5. **验证与局部视觉验收**：数字守恒、失败原子性、快照拆账、场景隔离为必要测试；检查原始样式与基准文件未变。按用户最终参考检查网格居中/小 padding、卡外进度、中性背景、下方传输线和统一播控。不以“奖项级”代替实际验收。
