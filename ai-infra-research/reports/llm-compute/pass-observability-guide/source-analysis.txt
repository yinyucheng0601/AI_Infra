我核对了你提供的《四框架编译 Pass 对比》（2026-10-19）。这份研究对我们之前讨论的 Pass 可视化有很大帮助，因为它不再简单按照编译阶段分类，而是提出了五类编译决策：规范化、降级、硬件映射、正确性保障、组织与交付，并将硬件映射进一步拆为空间、时间、并行单元、融合与调度。

但我认为，这五类适合作为编译器能力分类，不应该原样变成开发者工具的导航结构。

原因在于编译器的职责与开发者的诊断任务不是一一对应的：例如 Buffer 复用涉及空间规划，也会影响 Pipeline；同步插入属于正确性保障，同时直接影响并行执行效率。如果按 Pass 的内部分类设计工具，开发者要跨多个分类才能查清一个问题。

我的建议是采用双层模型：
- 底层保留编译器分类：记录每个 Pass 的实际名称、顺序、输入输出、职责、参数及其所属工具链。
- 上层按照开发者诊断对象组织：将计算、Layout、Memory、Pipeline、Sync、Instruction、Runtime 等跨 Pass 的对象串联起来。

原有认识或文档结论	核对结果	对可视化设计的影响

二、优化后的 Pass × 观测对象 × 诊断问题
我建议用 12 类可观测对象，覆盖五类编译职责，同时满足 PyPTO / TileLang-Ascend / Triton / cuTile 的横向比较需求。

这张表按开发者排查问题时的典型逻辑排列，不代表 Pass 的实际执行顺序。

这版相比之前最大的改变，是把几个以前混在一起的对象拆开：
- Data Layout 与 Memory：前者回答数据怎么组织，后者回答数据占据什么存储资源。
- Data Movement 与 Pipeline：前者描述移动了什么，后者描述何时移动、能否重叠。
- Pipeline 与 Synchronization：前者追求有效执行，后者负责维持必要的依赖约束。
- Tile & Parallelism 与 Instruction Mapping：前者决定如何分工，后者决定最终使用哪类目标操作。
- Validation 与编译过程：验证不是单个末尾 Pass，而是一套贯穿编译前后、并连接运行时的证据机制。
三、从 12 类观测对象进一步归纳成 5 种可视化
12 类对象不意味着需要 12 种图表。我建议将它们组织成五种相互关联的视图，让用户从宏观编译流程逐步进入具体问题。

01 / Pass Timeline — 编译演化视图

按真实执行顺序排列 Pass，并在 IR 表示发生变化的位置设置明确的阶段边界。点击一个 Pass，展示 Before/After IR、对象增删、编译耗时和所触发的诊断信息。

覆盖：IR Structure、Lowering，以及全部 Pass 的时间顺序。




02 / Mapping View — 空间与硬件映射视图

展示逻辑 Tile 如何被划分并分配到执行单元、数据采用什么 Layout、位于哪个 Memory Space，最终映射到哪些目标操作。允许在不同 Pass 之间对照同一 Tile 的变化。

覆盖：Tile & Parallelism、Data Layout、Memory、Instruction Mapping。




03 / Execution View — 执行流水与同步视图

使用泳道区分计算、数据搬运和同步。为 Memory 的申请、释放、读、写提供独立语义，并区分 AIC、AIV 以及相关流水的不同执行角色。静态编译调度和实测执行时间应使用明确的模式区分。

覆盖：Data Movement、Pipeline、Synchronization、Instruction Scheduling。




04 / Dependency View — 任务与通信依赖视图

以 DAG 呈现 Task、Kernel、数据生产者与消费者，以及跨核或跨任务通信。区分数据依赖、控制依赖和同步依赖，不把所有关系画成同一种箭头。

覆盖：Task & Communication，以及跨范围的 Synchronization。




05 / Diagnostics View — 编译与运行诊断视图

将 IR 校验、Pass 前后差异、异常诊断和运行时性能证据关联到具体对象。优先显示异常由哪个 Pass 首次引入、在哪个阶段被发现，以及哪些结论已有证据支持。

覆盖：Validation & Runtime，并支持对其他四种视图进行定位。



四、面向 PyPTO 的优先级
根据文档中 PyPTO 与 PTOAS 的职责分工，我会进一步调整实现优先级。尤其是 PyPTO 已有逐 Pass IR 快照、IRProperty 校验等基础，前端观测可以利用这些能力；但涉及 PTOAS 内部决策时，仍需要相应的 Pass 输出、诊断或调度信息，不能仅靠解析最终 PTO 代码还原全部中间过程。

优先级	先做什么	为什么
P0	Pass Timeline + IR Diff	建立全部调试信息的统一入口及对象追溯基础
P0	Memory / Layout Mapping	直接对应 Tile 算子开发中的资源、切片和布局问题

P1	Instruction Mapping	建立高层 Tile Op 到 PTO 目标操作的可追溯关系
P1	Task & Communication DAG	体现 PyPTO 任务编排及通信相关编译能力
P2	跨框架对照	在观测对象及语义已经稳定后，再比较不同编译链的实现差异
这里的 P0/P1/P2 是建议的产品实施顺序，不是对框架技术成熟度的评价。
五、我建议保留的一个重要设计原则
Pass 是变化发生的位置，Object 是变化的主体，Diagnostic 是开发者对变化的解释。

三者应有明确的数据关系：

证据层连接原始 IR、转换日志、校验结果与硬件性能数据。
例如，在 memory_reuse 之后，同一个 Buffer 的生命周期发生变化，UI 不应该只高亮 IR 文本中的几行差异，而应能定位到这个 Buffer，展示复用前后的 Live Range、共享的存储空间，以及是否存在潜在的读写冲突。如果存在风险，再关联到具体的同步 Pass 及其处理结果。

还有一个容易遗漏的技术前提：跨 Pass 对象身份不能完全依赖 IR 的 SSA 名称或行号。 Lowering、融合、切片和代码生成可能使一个对象拆成多个或多个合并成一个，因此应支持一对多、多对一和无法确定来源的映射关系，避免制造虚假的完整追溯。

从产品设计角度，我认为最终应该建立的是：

Object-centric Compilation Observability（以对象为中心的编译可观测性）。

Pass Timeline 用来说明编译过程；Mapping、Execution 和 Dependency View 用来解释具体发生了什么；Diagnostics 则将这些变化与正确性、性能问题联系起来。

这样既能保留专业开发者需要的逐 Pass 精确性，也能把 PyPTO、TileLang、Triton 和 cuTile 的差异统一到有意义的用户问题上。尤其对于昇腾算子开发，它能够清楚分辨：哪些是上层编译器作出的规划，哪些是在 PTOAS 等下游工具链中决定的，以及哪些结论已经获得实际硬件执行数据的验证。
