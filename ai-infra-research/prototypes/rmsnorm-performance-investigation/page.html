RMSNorm · 使用与扩展
CANNBot 增强了什么
本工具使用 CANNBot 的 ops-theoretical-performance-estimation。它补充的是 Codex 原本没有随带的硬件标定数据与可执行性能模型，让源码中的计算、搬运和容量条件能够得到有依据、可复算的性能估算。
Codex 可以读取 Kernel、推导计算量与读写量，也可以编写 Roofline 公式。但没有对应硬件的测量记录时，无法仅凭源码可靠确定指令实际吞吐、不同搬运规模下的带宽，以及指令和流水之间能重叠多少。这些参数需要硬件测量或其他明确来源，不能由推理替代。
  • 有来源的硬件参数：使用仓库保存的指令吞吐、读写带宽曲线和重叠标定记录；具体字段仍区分实测、公开表与推导默认值。
  • 可执行的定量估算：原引擎接收计算流、数据量、UB 使用和核分配，输出 MTE2、Vector、MTE3 的资源总需求、瓶颈分类与理论时延。页面因此能够比较方案的性能代价，而不只展示“多读一次”。
  • 可复算与核对：开源 RMSNorm Kernel、计算流定义、标定一致性和回归检查，提供从图中数值追溯到实现、模型输入及参数来源的依据。
在本工具中的具体结果
例如 FP32 [2048,16384]：整行模型 live 为 320 KiB，超过可用 UB 248 KiB，因此选择两遍分块，并计入 128 MiB 的额外 X 重读。原引擎结合对应带宽与资源重叠模型，得到 179.024 µs 的理论时延，并将瓶颈归为 mte2_bound。这些性能结果依赖 CANNBot 提供的数据和执行模型；字节数与容量条件本身则可由源码独立推导核对。
本页先离线调用原引擎，再保存各配置的输入、输出与固定版本来源。切换配置时展示对应结果；浏览器没有临时猜测硬件参数，也没有修改标定常量来迎合预期。事件顺序和队列申请／释放来自 Kernel 核对，未把资源总耗时拆成虚构的逐事件时间戳。
使用
从左下选择输入；有两种可行实现时可切换，只有一种时显示当前实现。“硬件映射”打开角落的 950 架构联动窗口。点击执行事件或 Tensor 查看来源；“队列复用”按 AllocTensor / FreeTensor 展示队列的多次申请和释放。右上依次为核查、当前选择、源码、教程。检查器允许编辑问题、复制与导出；平移和缩放不会改变选择。
使用 ai-infra-investigation，读取本页导出的 RMSNorm 选择与固定提交源码。核对 flow 与 rms_norm_full / rms_norm_split 的 gamma 请求、UB 分配、VF 与分块归约对应关系。保留原标定常量，区分模型差异、源码参数和设备观测；提出最小上板对照实验。
扩展
本页保存五个上游配置与两个 FP32 驻留边界实验。新 shape 或硬件需通过 collect.py 重新调用原引擎；浏览器不冒充实时 Python 引擎。BF16 只核对 flow，附带直调 Kernel 为 FP32。设备结果可按上游 compare.py 接入，当前页面没有本机 NPU 测量。PTO 图为 950B 局部拓扑，估算参数来自固定 9589 数据；图中的 AIC 与 AIV 1/2 不表示全部 64 个 VectorCore。
方法与边界
CANNBot 使本机没有 NPU 时也能运行这套估算与离线检查，但不等于已验证预测精度。当前没有本机 NPU 实测；理论时延和瓶颈分类仍需独立上板对照。资源数值表示模型总需求，不是实际执行时间轴。稳态重叠与填充排空由引擎计算，不能把三条耗时直接相加。核查项反映源码与抽象模型的粒度差异，不等于设备故障。来源数据包含测量、公开表和推导默认值，按具体字段溯源。
