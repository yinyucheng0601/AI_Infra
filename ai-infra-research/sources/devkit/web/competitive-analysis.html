分析方法与范围

按四阶段流水线执行：规划 → 搜集 → 分析 → 可视化。分析视角为 UX——聚焦任务流、信息架构、交互模式与可用性，而非功能清单或商业模式。

目标

为 Kunpeng DevKit AI 的框架、交互、布局决策提供依据。不做泛泛的产品测评，只回答"我们该怎么做"。

为什么跨四派

TUI 分辨率模型 · Cell 是区别于 GUI 的根本约束

现代 TUI 不能再简单分成"低分辨率字符界面"和 GUI 两类。更准确的做法，是看它的主 UI plane 到底用什么分辨率表达。TUI 产品没有固定的 1920×1080——它跟着 Terminal 窗口变化，现代图形协议则可能让某个区域额外获得 pixel resolution。

纯 Cell TUI · OpenCode

OpenCode 使用 OpenTUI 作为底层 UI core，支持 component、layout 等现代 UI 抽象，但最终仍是在 terminal 中绘制。假设 Terminal 窗口 1440×900 px，字体 cell 约 9×18 px，布局坐标约 160 columns × 50 rows。它看到的不是 x=183px, y=764px，而是 column=18, row=42, width=124 cells。Panel、border、input、scroll——这些元素的边缘仍然只能落在整数 column。设计语言越来越 GUI-like，但空间分辨率仍是纯 Cell。

关键洞察：OpenCode 同时有 Desktop App，恰好说明同一个产品逻辑可以有 TUI frontend 和真正的 GUI frontend。

纯 Cell TUI · Lazygit

120×40 cells 的 Terminal 中，Lazygit 的逻辑 UI resolution 就是 120×40 = 最多 4,800 个"空间格子"。当然每个格子还携带 glyph、foreground、background、bold、underline——所以不是 4800 个黑白像素，但 geometry resolution 就是这个量级。

Sub-cell TUI · btop

btop 使用 Unicode Braille 字符画 graph。一个 Braille glyph 内部可表达 2×4 = 8 个 dot。40×10 cells 的 graph 区域，普通 grid 只有 40×10，用 Braille 则视觉采样网格 ≈ 80×40 dots——比纯字符精细很多。

但仍不是 pixel graphics：程序只发送 U+28XX Braille glyph，Terminal Emulator 再用字体 rasterize。管线是 data → dot pattern → Unicode char → cell → font raster → pixels，而非 data → drawPixel(x, y)。

从 TUI Design System 视角：分辨率不是单一值，而是三套 Token
① Layout Resolution — 布局分辨率 cols × rows

② Cell Resolution — 单元格物理像素 单个 cell 的 px 尺寸
e.g. 9 × 18 px/cell
↓ 查询终端能力 ↓
③ Graphics Resolution — 图形协议支持 pixel-addressable?
none / sixel / iTerm / kitty

FLOOR 06

模式识别

通用模式 · 多个竞品收敛到同一答案

M1 · 帮助提示是"当前状态的函数"

表现：k9s 的 Menu 由导航栈驱动、lazygit 的 options 行由 context 驱动、Zellij 的提示条由当前模式驱动、btop 把键位画在它作用的那个盒子边框上。

为什么有效：避免了"一张巨大的全局键位表"。用户在当下的位置学当下的键，认知负荷随时间摊薄而非一次性堆满。

代价要算清：Zellij 的常驻提示条约占 5MB 内存——发现性是有实打实成本的。

M2 · 布局可变性用"预设循环"而非"拖拽调整"

表现：btop p/P 循环 9 套 preset；lazygit +/_ 循环 normal/half/full。

为什么有效：终端里拖边框成本高、精度差。一键循环到"下一个够用的布局"比精确调尺寸更符合实际使用节奏。

反证：Zellij 支持任意递归分割，但鼠标不能拖拽调尺寸是它被吐槽最多的点之一——说明"自由度高"并不等于"好用"。

M3 · 命令面板是唯一可扩展的发现性入口

表现：k9s : + 别名 + 补全、OpenCode ctrl+p、Claude / 菜单统一命令/skill/plugin/MCP。

为什么有效：能力数量增长时，视觉罗列（MobaXterm 的 Ribbon）会变拥挤，模糊搜索不会。

k9s 的反例值得注意：:xray 这类命令在 ? 和别名视图里都找不到——有面板不等于可发现，命令本身也要能被搜到。

M4 · 折叠低信号输出

表现：Claude 工具结果默认折叠、MCP 调用折成一行、/focus 极简视图。

为什么有效：Agent 会产生大量读文件类的低信号操作，不折叠就会淹没真正需要人看的写操作。

反证：OpenCode 完整 diff 内联无折叠，500+ 行糊一屏，社区专门开 issue 要折叠模式。

M5 · 选中联动（master-detail）

表现：lazygit 左选什么右画什么（最彻底）；k9s Pulses 图表 Enter 跳到资源列表。

为什么有效：把"我关心哪个对象"和"这个对象的细节"在空间上绑定，省掉用户在两个视图间做心智翻译。

M6 · 零前置启动

表现：除 MobaXterm 外全部产品都是敲命令直接进工作台。

为什么有效：把配置成本从"开始前"挪到"需要时"，让第一次使用的门槛趋近于零。MobaXterm 的先建 Session 是上一代范式的遗留。

M7 🆕 · 渲染能力按区域退化

表现：btop 按盒子设定 braille / block / tty；Yazi 按协议链 fallback（Kitty → iTerm2 → Sixel → half-block → textual）。

为什么有效：不在整个应用层面做"最低共同能力"的妥协，而是允许不同面板按终端实际能力各自选择最优渲染精度。

代价：产品需维护 capability detection + fallback 逻辑，且不同终端的渲染效果会有差异——这是 TUI Design System 的 capability adaptation 问题。

W 鼠标捕获挡住原生复制（作者自陈）；context 覆盖全局键造成困惑（R 全局刷新、commits 里变 reword 且无确认）；菜单层级深。

O 它证明了"分区 + 联动"在没有任何图表的情况下也能做出高密度——我们可以在此之上叠图表。

T 其键位习惯（1-5 面板、? 上下文帮助）在 Git 用户中已成肌肉记忆。

Zellij

S 布局系统最强（KDL + swap layouts + 远程 URL）；UI 即 WASM 插件；会话序列化有版本契约；Unlock-First 分流设计。

W 默认独占 8 个 Ctrl 键（最高频吐槽）；鼠标不能拖拽调尺寸；边框妨碍复制；资源占用高于 tmux；KDL 有学习成本。

O 它把 UI 做成插件，但插件生态很小——说明可编程 UI 的价值不在生态而在自用的布局灵活性，我们不必追生态。

T 若团队已用 tmux/Zellij，我们的多任务框架会与之功能重叠，需想清楚边界。

Yazi 🆕

S 双重分辨率共存（Cell 布局 + Pixel 渲染）；完善的协议降级链（Kitty → iTerm2 → Sixel → Chafa → text）；图片解码与 downscale 高效。

W 不是 AI 工作台，交互模型不直接可搬；pixel 区域无法参与 layout 计算（sidebar 仍是整数 column）。

O 它的双重分辨率模型可直接参考——DevKit 的 chart/diff/架构图区域可在 Kitty-capable terminal 上升级为 raster 渲染。

T Hybrid 模式依赖 terminal 能力，不是所有用户都有 Kitty/WezTerm——必须维护 capability detection + fallback。

FLOOR 09

行业分歧点 = 创新空间

不仅看"我们 vs 竞品"，也看竞品之间在哪些问题上给出了完全不同的答案。尚未形成统一范式的地方，就是可以自主选择甚至定义的地方。

分歧① 分屏：要还是不要

Zellij 无限递归 + 浮动 + 堆叠 ｜ OpenCode 明确 not planned，让位 tmux ｜ Claude Code 不做面板，走多会话 + worktree ｜ lazygit 固定分区 + screenMode 缩放

我们的判断：AI Coding 派放弃分屏的理由是"对话是线性的，不需要并置"。但工程分析不是线性的——迁移报告要对着源码看、Trace 要对着算子表看。这是 DevKit 与通用 AI Coding 的本质差异，也是我们必须做分屏的理由。上限设 3 格（见框架章节）。

分歧② 权限：模型判断还是规则匹配

Claude Code 分类器模型做语义判断，把对话里的口头约束当硬约束 ｜ OpenCode tree-sitter 解析命令后纯规则匹配，最后匹配者获胜

我们的判断：工程场景更需要确定性与可审计——"为什么拦了我"必须能解释。倾向规则为主（可读、可版本化、可评审），模型判断作为补充提示而非阻断依据。

分歧③ Plan：模式还是 Agent

Claude Code Plan 是一等公民模式，有正式批准对话框、计划可外部编辑、接受后自动切权限档 ｜ OpenCode Plan 只是一个权限更严的 agent，无批准流程

我们的判断：站 Claude 一侧但要修正它被批评的地方——Armin Ronacher 的拆解指出 Claude 的计划"藏在文件夹里的 markdown"、用户掌控感弱。我们的 Plan 应就在界面里可见可改，且每步标注要调哪个 DevKit 工具。

分歧④ 发现性：常驻提示还是按需唤起

Zellij / k9s / lazygit 常驻提示条（Zellij 为此付约 5MB）｜ Claude / OpenCode 按需（? / which-key）｜ btop 第三条路：把键位画在它作用的那个盒子边框上

我们的判断：采 btop 的空间化思路 + lazygit 的上下文化——底栏只放全局与当前 Workspace 的键，面板级操作提示画在面板边框上。既不占一整行，又不需要用户去别处找。

分歧⑤ 🆕 分辨率：纯 Cell 还是 Hybrid

OpenCode / Lazygit 纯 Cell（全部 UI 边缘只能落在整数 column）｜ btop Sub-cell（Braille 把一个 cell 再细分 2×4 dot）｜ Yazi Hybrid（Cell 布局 + Pixel 渲染共存）

我们的判断：Hybrid 是趋势但不是万能药——pixel graphics 解决了 content rendering 精度，但没解决 layout model（Yazi 的 sidebar 宽度仍是整数 column，不能是 317.5px）。AI 工作台的核心价值在 layout model 而非 rendering resolution，但 chart / diff / 架构图预览场景值得做 capability adaptation：在 Kitty-capable terminal 上把这些区域升级为 raster 渲染，在普通 terminal 上 fallback 到 braille/block。

FLOOR 10

洞察与机会点

按差异化价值 × 实现成本排序。前三条是我们能建立护城河的地方，后面是必须补齐的行业基线。

01

把"审查确认"做成产品的强项，而不是行业通病的第 8 个复制品

情绪最低谷在这里，且七个竞品全都弱：两个 AI TUI 都没有 hunk 级 accept/reject，diff 要么刷屏要么只能按工具调用整体批准，撤销还只覆盖一部分。

我们的打法：① 文件级折叠 + 摘要优先（避开 F3）；② 每条改动挂 Evidence（知识库案例号 + ARM 手册章节 + 源码行号），把"我为什么该同意"变成可点开验证的；③ 逐文件 A/E/R 而非一次性全批；④ 撤销显式声明覆盖边界，不给假安全感。

这条同时是 DevKit 的天然优势——迁移改动本来就有知识库依据可引，通用 AI Coding 工具引不出来。

02

分屏 + 选中联动：AI Coding 派的集体空白

Claude Code 无分屏、OpenCode 把多窗口需求 closed as not planned。而 lazygit 证明了"左选右画"是高密度工程工具的成熟范式。

我们的打法：Canvas A/B 双栏 + P22 联动，把"结论 ↔ 证据"做成常驻空间关系。再叠一层MobaXterm 式的跟随——Agent 改到哪个文件，工程树自动定位到哪。联动不只发生在用户点击时，也发生在 Agent 行动时。

03

配置补齐做成一等公民流程

没有任何一个竞品把"执行中发现缺配置"做成正式的暂停-解释-补齐-续跑流程。最接近的是权限弹窗，但它解决的是"允不允许"，不是"缺什么"。

我们的打法：P27 已定义。关键是三点——就地暂停不回滚、解释为什么这一步需要它、非敏感项记忆复用。

04

数据可视化：把观测派的密度带进 AI 工作台

两个 AI Coding TUI 几乎没有图表能力，而 btop 的 braille/block/tty 三档分级 + 按盒子设定精度是成熟方案。Yazi 更进一步——在 Kitty/WezTerm/iTerm2 capable terminal 上把 preview 区域升级为真实 raster 渲染。

我们的打法：T0–T4 渲染分层已定义。可直接借鉴 btop 的两点——渲染精度分档打包进 Workspace 预设（切视角时同时切精度）；颜色承载额外维度（btop 用明度编码"离选中行的距离"，我们用色阶编码利用率）。更进一步：在 Kitty-capable terminal 上把 chart / 架构图 / 拓扑图区域升级为 pixel rendering（参考 Yazi 的双重分辨率模型），普通 terminal fallback 到 btop 式 braille/block。不同面板可以有不同的渲染精度档位——这是 M7 的核心启示。

05

终端原生能力的逃生舱：抄 Claude 的 [

F1 是三派全中的行业级失败。Claude Code 的 [（把 alt-screen 对话吐回终端原生 scrollback）是目前唯一正面回应这个矛盾的设计。

我们的打法：① 提供"吐回 scrollback"键；② 一键关掉所有边框装饰进入纯文本模式（对应 Zellij 的边框挡复制问题）；③ 键盘文本选择必须有（Zellij 缺这个被用户当作回退理由）。

06

布局预设循环 + 数量变化自动重排

M2 已证明"预设循环 > 拖拽调整"。Zellij 的 swap layouts 再进一步：pane 数变化时自动重排。

我们的打法：F1–F4 Workspace 预设已定义，补一条——Canvas 数量从 2 变 3 或从 3 变 2 时自动切到对应的预设比例，不要求用户手动重调。

07

工具调用透明化：抄 lazygit 的 command log

lazygit 把每个按键背后的真实 git 命令打出来，既是调试面板也是学习通道。

我们的打法：P11 Tool Card 已有"工具名/输入/耗时/结果"四要素，再加一行等价 CLI 命令——让用户知道 Agent 到底在跑什么，也让他们能把这条命令拿去脚本里复用。这对 DevKit 这种"CLI 已有等价物"的产品几乎零成本。

08

反空转：抄 OpenCode 的 doom_loop

同一工具连续调用 3 次自动触发询问。迁移大工程时 Agent 反复重试同一个失败步骤是很现实的浪费。

我们的打法：作为 P10 Approval 的一个触发条件加入，不需要新 Pattern。

一句话总结这次分析：AI Coding TUI 在意图表达上大幅领先传统工具，但在审查确认与空间组织上集体退化到了比 lazygit、btop 更弱的水平——因为它们默认"对话是线性的"。Kunpeng DevKit AI 的机会正在这里：把观测派的空间密度与联动、工作台派的布局能力，接到 AI 派的意图表达之上。
FLOOR 11

补充观察 · 实拍截图里的九个具体做法

来自 MobaXterm、OpenCode（splash / diff）、opencode-kanban、SysWatch、euporie、TUI 媒体库、SimUtil、Rebels in the Sky、term-rex、Pinstar 的实拍界面。这些是比"空间范式"更细一层的实现细节，但每一条都直接对应我们的某个待解问题。

① Token 级 diff 高亮 直击机会点 01

OpenCode 的 diff 不是整行标红绿，而是只把变化的那个 token 反色高亮——`variant="primary"` 里只有 primary 那一小块是高亮的，`danger` 同理。

62  62  <Button
64  64   type="submit"
65    variant="primary"
   65+ variant="danger"

为什么值得抄：整行高亮时，一行里改了 3 个字符和改了 30 个字符看起来一样重。token 级高亮让"这次到底动了什么"一眼可见——这正是行业最弱环节（审查确认）里最低成本的改进。_mm_pause() → asm("yield") 这类替换尤其受益。

② Insights 面板 + 跳转箭头 P26 + P22 的已验证实现

SysWatch 在仪表盘底部有一个常驻 Insights 区，形态是严重度标签 + 一句话结论 + 跳转目标：

Insights — 2 active (press [+] for detail)
CRIT runaway process — yes (pid 28540) sustained 100% CPU  → Procs
CRIT GPU pegged — 98% util sustained over last 6s        → GPU

这就是我们 P26（AI 标注层）+ P22（联动下钻）的现成形态，而且被一个真实产品验证过。关键三点：常驻但不抢戏（底部一条）· 结论必须带具体证据（pid / 持续时长）· 右侧箭头直接跳到对应面板。我们的 AI 判断可以完全沿用这个形态。

③ 编号 Tab 栏 = 键盘直达

SysWatch 顶栏：[1] Overview [2] CPU [3] Memory [4] Disks [5] FS [6] Procs ...——编号即快捷键，不用另记键位表。lazygit 的 1-5 面板跳转是同一思路。

对我们：Workspace 切换用 F1–F4 已定，但多任务 Tab 也应显式编号（Alt+1..9），且编号要画在 Tab 上而不是只写在帮助里。

④ 面板标题嵌在边框上

opencode-kanban 与 SysWatch 都把标题写进面板上边框：┌Tasks by Category、┌Logs | structured | e/Enter toggle。标题行不额外占一行，且可以在同一位置塞下操作提示。

这与 btop"把键位画在盒子边框上"是同一招——边框是被浪费的一整圈空间。我们的框架规范已定 title-2 嵌入上边框，这里再补一条：右侧可挂当前面板的操作提示（如 e/Enter toggle）。

⑤ Splash 兼作速查表

OpenCode 启动页在像素 Logo 下直接列出核心命令与快捷键：/help /editor /models /init /compact /sessions + 对应 ctrl+x ?。

我们的 Landing 屏已有"最近 / 建议"两行。可再补一列常用命令速查——首屏是唯一一次用户愿意读说明的时刻，别浪费。

⑦ 推翻一个假设：终端能渲染真图形 补入 T5 层

此前整份规范默认"终端只能画字符"，所以把复杂图表都往字符网格上压。这个前提是错的。实拍证据：euporie 在终端里渲染 matplotlib 图表、LaTeX 公式、HTML/CSS 表格，还有按钮/开关/滑块/下拉/颜色选择器等真 UI 控件；TUI 媒体库渲染电影海报；SimUtil 把手机模拟器画面嵌进面板；甚至有人在终端里跑 Pokémon（55 FPS）。

协议终端特点
Kitty graphicskitty · WezTerm · Ghostty · Konsole性能最好，支持动画与层叠，可与文字混排
Sixelxterm · mlterm · foot · WezTerm最广泛的老协议，色深受限

对我们的影响：火焰图、Pass-IR 依赖图、精确 Roofline 这三类"字符网格做不好"的图，现在有了正解。但纪律更严——T5 是增强不是基础，每处都必须有 T2/T0 降级（ssh 到鲲鹏服务器的默认环境大概率不支持），且永不用 T5 做框架：Chrome 层永远是组件，图形只进 Canvas。

⑧ 反色键位 chip 已用到 Demo

Rebels in the Sky 底栏把按键做成反色小块、动作用常规文字：Esc Quit  ↑/↓ Select  ↵ Confirm

比纯文本 keybar 易扫读一个量级，且不占额外行。零成本，直接抄。

⑨ 节点画布 + 鼠标交互

Pinstar（终端 canvas 编辑器）用彩色边框盒 + 虚线连线做自由画布，支持鼠标拖拽平移、Ctrl+j/k 缩放、Tab 切焦点。

对应我们的 P04 Diagnosis Graph 与依赖图：不必是静态 ASCII，可以做成可缩放可平移的交互画布。节点少时用它，节点多时上 T5。

⑥ 反面：MobaXterm 的信息密度失衡

实拍里 MobaXterm 的终端区被彩色日志填满（每行都有颜色），但颜色没有分层——Information / Warning / Error 三种级别与文件名、路径、命令混在同一套配色里，读起来全是噪音。

对照我们的纪律：语义色只上字符与短标签，不上整行文本。日志渲染应该是"级别标签着色 + 正文中性"，而不是整行染色。
