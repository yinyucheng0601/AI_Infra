## 01 · 为什么智能计算需要专门的视觉设计体系？

页面锚点 `#domain-theory`

想象一根下载进度条，你脑中这个进度条是很顺利地加载完了，还是卡在某个点不动了？

我们作为 C 端用户，看到进度条卡住都很习以为常了。是不是网络不好？或者这个进度条是不是“骗人的”？

计算领域的开发者，其实也会面对这样一根进度条。一个计算任务跑到哪里了，为什么这里特别慢？但这根进度条背后，需要打开的黑盒就多得多了。我初步归纳了四个方面。

1. **领域知识。** 不管是在开发一个小算子，还是让一个 DeepSeek 这样的大模型跑起来，背后都涉及大量专业知识。开发者需凭经验把这些知识关联起来，才能理解眼前发生了什么。

2. **计算机制。** 同样是“这里耗时特别长”，究竟是在等内存数据搬运，还是存在资源争用？这就涉及硬件约束，需要结合证据进一步判断。

3. **人的认知。** 你认为开发者更想看到的是一根进度条，还是成千上万条时序记录？只看进度条，可能解释不了问题。把所有数据展开，他也很难一下找到重点。开发者本身就面对海量数据，注意力非常宝贵，所以我们也需要把 C 端设计中关于认知负荷、信息层级和反馈的经验带进来，约束视觉展示什么。

4. **Agent 的工程能力。** 在今天这个 AI 时代，开发者看到任务卡住，第一反应可能是什么？问豆包！派一个 Agent 去调查。通用的 Agent 还不够。它需要具备领域知识，理解计算机制，才能组织数据、关联证据，按开发者当前需要的深度来呈现，帮助他理解结果，并决定下一步怎么做。

从这四个方面出发，我推导出 Agent 协同时代，我们的一个基本设计任务。**帮助开发者理解复杂计算系统，并依据运行证据作出决策。**

## 03 · 让可观测性辅助开发者理解与决策

页面锚点 `#language`

围绕刚才这个设计任务，我归纳了三个设计原则：证据驱动、认知减负、协同控制。这三个原则，其实也能对应到我们做交互设计时很熟悉的几个问题。

**第一个是证据驱动。开发者现在需要看什么？**

可以是一次运行的报错、关键异常点，甚至是 Agent 初步排查后一些值得关注的检查点。

**第二个是认知减负。这些信息，一次需要看多少？**

这也是设计师很熟悉的信息层级和渐进披露。和 2.0 相比，理念共识在于不是所有场景都需要复杂可视化。一个摘要就能回答的问题，我们就先给摘要。需要比较多个对象时，再展开它们的关系。需要深入调查时，再进入细节。而且从整体进入局部的过程中，要让他始终知道自己在看哪里、当前选中了什么。

**第三个是协同控制。看完以后，开发者能做什么？**

我们做可用性设计时，会考虑反馈是否清楚、操作是否可控，以及出现问题后能不能纠正。到了 Agent 协同的场景，这些要求仍然成立。Agent 给出了一个解释，开发者需要能检查它的依据。觉得某个条件有问题，需要能调整参数、看看影响。有了新的判断，还需要把当前对象、条件和证据一起交回 Agent，让它接着调查。这样，开发者的判断才能真正介入，而不是靠盲调代码或者和 AI 无休止对话。

## 04 · 以共享时间轴解释并行执行关系

页面锚点 `#attention`

### 章节开场

前面明确了设计任务，也有了三个设计原则，那具体怎么落实到设计里？

这里我借用了设计师很熟悉的双钻模型，提出开发者人机协同三钻模型。人和 Agent 可以共同参与探索和收敛。

我们先看第一个阶段，聚焦。**哪里值得我看？** 当 Agent 带回来一批调查结果时，我们怎样帮助开发者找到重点，同时保留他继续核查的依据？接下来用执行泳道这个案例展开。

### 案例正文

之前 2.0 的泳道界面里有非常密集的任务条、颜色和文字标签。它们提供了丰富的执行信息，但当开发者带着一个具体问题进来，比如“这次运行为什么慢”，还是需要自己从里面寻找、比较。

所以我想做的是，围绕当前问题建立视觉层级，让值得关注的差异更容易被看到。

首先，总览的认知负担减轻了很多。这里可以看到，第 6 条泳道最晚进入运行阶段。顺着这个差异往下看，当前这组记录的 54 个步骤中，它有 53 次都是最晚进入的，所以值得继续调查。

这里展示的是 Host 端的调用记录。回到开场的进度条，这些记录能帮助我们发现哪一路进得晚，给后续调查一个起点。

## 06 · 以可计算交互支持人机协同验证

页面锚点 `#agent`

### 章节开场

前面帮助开发者找到重点，也理解了相关关系，接下来就是第三个阶段，介入。我看完之后，能做什么？

比如 Agent 给了一个解释，开发者觉得某个参数或者共享关系可能有问题，可以调整条件，再看看结果有什么变化。
所以这里的设计，需要把理解和操作连接起来，并且保留当前的问题、条件和证据，方便交回 Agent 继续调查。

### 分镜 01

接下来这个案例就用一个比较简单的计算 OP，说明开发者怎么参与核查。这里是一个 Scale 计算，可以简单理解为输入乘以一个倍率。这个例子里，两批输入共用了同一个倍率。

首先选中这个参数，画面会把它影响的输出标出来。这样开发者在修改之前，就能先看清影响范围。

### 分镜 03

接着，把倍率从 −1 改成 1，可以看到两批对应的输出都发生了变化。

### 分镜 04

需要核查的时候，再展开具体算式，看看变化是不是符合预期。这里用参考计算演示这个核查过程。

### 分镜 05

## 07 · 将领域视觉知识沉淀为 Agent 可执行的设计规则

页面锚点 `#system`

### 章节开场

前面三个案例，分别讲了怎么帮助开发者聚焦、理解和介入。那接下来一个问题是，换一个模型、算子或者调查任务，这些设计怎么继续复用？

这里我把可以复用的内容整理成了图元、Pattern 和页面框架，再通过 Skill 把选择和使用它们的规则串起来。

这样，Agent 具备的设计能力会自我不断优化提升。

### 分镜 01

先看图元。模型、张量、内存和计算单元这些对象，需要有相对稳定的视觉表达。这样换一个场景，开发者仍然能认出它们，Agent 生成的时候也有共同的规则。

### 分镜 02

再看 Pattern。比如刚才的执行泳道、模型层级和参数联动，它们分别适合表达时间关系、层级关系和计算影响。这里把适用问题、对象关系和交互方式一起整理下来，方便按任务选择。

### 分镜 03

然后是页面框架。主体画布留给当前要理解的对象，场景切换、阶段导航和视野控制放在周围，细节在需要时原位展开。这样既保留操作入口，也能给复杂关系留下足够的展示空间。

这里再用一个内存案例，看看这些设计怎么组合起来。

画布展示了四路绑定指向同一个内存地址，开发者可以选中对象，对照相关记录。但共用地址是否造成覆盖，还要继续检查它们各自的写入、读取和生命周期。所以核查面板会把已有记录，以及还需要补充的问题放在一起，方便继续调查。

### 分镜 04

这也对应了 Skill 的工作流程。先明确工程问题和现有证据，再决定需要表达什么关系，组合已有的图元、Pattern 和框架，最后核查对象绑定、交互和来源。

工程数据和验证能力来自开发者及相关工具，我们把这些证据组织成便于理解和核查的视图。证据还不够，就继续补证据。表达没有帮助判断，就调整视图。

从领域知识、计算机制、人的认知和 Agent 工程能力出发，我归纳了证据驱动、认知减负和协同控制三个原则，再落实到聚焦、理解和介入三个阶段。

前面的案例分别尝试帮助开发者找到值得关注的异常、沿着同一个对象理解复杂关系，以及核查解释、调整条件，把判断交回 Agent。

最后，再把这些设计判断沉淀成图元、Pattern、框架和 Skill，供不同任务复用。
