# AI Infra 视觉设计体系评审与优化建议

## 一、核心结论

我建议保留你现有的「聚焦—理解—介入」三原则，但将它从体验原则升级为一套有明确工程语义、视觉表达规则和验证标准的设计方法论。

你现在的体系已经有较好的基础，特别是三点：

- 问题驱动：从异常和判断任务出发，避免把复杂计算过程完整地倾倒给用户。
- 对象连续：通过 Layer Stack 等案例，让用户在不同尺度之间保留工程对象的身份和上下文。
- 人机协同：通过 Scale 案例，将参数核查、关联输出和证据导出衔接到 Agent 工作流。

这三个主张符合面向开发者的专业工具方向，并且已经有相应的可视化案例支撑。

不过，目前体系仍有一个主要问题：

「聚焦—理解—介入」清晰地描述了用户应该获得什么体验，却还没有完整定义设计师如何从工程问题推导出具体视觉方案。

例如，在你的框架下，设计师知道应该保留对象连续性，但仍需要回答：什么情况下使用 Graph、Timeline 或 Memory Map？如何表达静态依赖与运行时事件的差异？如何定义对象跨层映射？什么证据足以支持一个诊断结论？

这正是下一轮优化应该补充的内容。

这里需要澄清：五层不是要求用户按顺序走完五个页面，而是设计师分析工程问题时应检查的五个维度。某个简单且确定的任务，可能只需要对象和数值摘要；只有涉及复杂关系或不确定判断时，才需要逐步展开更多维度。

因此，它与你现有的「生成最少但足够的可视化」完全兼容。

## 四、最值得优先优化的五项内容

### P0 · 1. 增加「问题 → 视觉表达」的决策规则

这是目前最重要的缺口。

你已经定义了图元、Pattern、页面框架，但还需要建立选择依据，避免 Agent 遇到复杂问题就生成大量图表。

建议增加一个 Visualization Decision Matrix：

| 工程问题     | 关键关系       | 优先视觉表达                   | 关键交互        |
| -------- | ---------- | ------------------------ | ----------- |
| 数据如何计算   | 计算依赖       | DAG / Compute Graph      | 节点展开、上下游追踪  |
| 数据如何分布   | 空间、布局映射    | Tensor Grid / Layout Map | 维度切换、索引追踪   |
| 为什么等待    | 时序、同步依赖    | Timeline + Dependency    | 同轴对齐、事件定位   |
| 内存如何复用   | 地址、生命周期    | Memory Map + Timeline    | 生命周期高亮、地址关联 |
| 编译发生什么变化 | 版本与结构映射    | Before / After Diff      | 差异定位、来源追踪   |
| 系统瓶颈在哪里  | 资源、事件、因果候选 | Topology + Timeline      | 跨视图联动、证据检查  |

核心约束：先判断用户要理解哪种关系，再选择可视化类型。

例如一个 Kernel 数据依赖问题，首先应该选择 Dependency Graph，而不是因为 Timeline 更具有视觉表现力就优先使用 Timeline。

### P0 · 2. 把「对象连续」升级为可执行的跨层映射规范

当前 Layer Stack 展示了从模型整体、Layer、Query Activation 到张量采样的连续探索，这是很好的案例。

但对于算子开发，还应该继续覆盖：

`Source → IR → Tensor/Tile → Buffer → Instruction → Runtime Event`

这里最重要的是明确对象之间的映射基数：一对一、一对多、多对一，或者无法建立精确映射。

例如经过算子融合和编译优化后，Source Operator 与 Kernel 不一定一一对应。

建议每种跨层 Pattern 明确：

- 对象的稳定身份与版本。
- 当前所在的分析尺度。
- 上下游对象映射。
- 选择如何跨视图传播。
- 不能建立精确映射时如何表达。

这样你提出的「对象连续」就可以从用户体验原则，变成 Agent 能够遵守的技术规范。

### P0 · 3. 将「证据可核查」升级为证据驱动设计规范

当前执行泳道案例做得比较好的一点，是明确区分了 Host 观测窗口和设备根因结论，避免直接把事件相关性解释为因果性。

建议将这种严谨性推广到整个设计体系。

| 证据层级         | 定义             | 视觉要求       |
| ------------ | -------------- | ---------- |
| Observed     | 实测或直接采集的事实     | 显示数值、来源、条件 |
| Derived      | 根据事实计算得到的结果    | 支持查看计算依据   |
| Hypothesized | 基于证据提出的解释      | 明确假设及待核查项  |
| Validated    | 经过指定检查或实验支持的结论 | 显示验证方法和结果  |

它应该成为每个 Pattern 的语义要求，而不是额外添加一套状态标签。

例如数据缺失时，不要用模拟值填充成完整曲线；因果关系尚未建立时，不应该直接绘制确定性的根因传播链。

### P1 · 4. 补充「动态行为」设计 Pattern

目前的执行泳道展示了时间关系，但动态行为还包括状态转换、资源占用变化、数据生命周期和并发执行。

建议首先增加三个通用 Pattern：

Execution Pattern：时间轴、并发、同步、等待和关键路径。

Memory Lifecycle Pattern：分配、写入、读取、复用、释放及与计算阶段的关联。

State Transition Pattern：编译状态、请求调度状态、Buffer 状态、Agent 任务状态的转换。

其中 Memory Lifecycle 很适合作为算子开发的下一个代表案例，因为它能够同时验证对象、空间映射、时间行为和证据约束。

### P1 · 5. 将「介入」延伸到完整的优化验证

当前 Scale 案例已经支持用户选择参数、核查关联输出、保留问题上下文并交给 Agent。

下一步应该增加修改之后的验证衔接：

发现问题

调整条件

Agent 执行

Validation · 修改后验证

Correctness

数值正确性

Performance

性能变化

Diff

修改影响

这能够将你当前强调的 Human Intervention，从「用户能够介入 Agent」进一步推进到「用户能够决定是否接受 Agent 的结果」。

## 五、对现有三个案例的具体建议

| 当前案例               | 已经体现的设计价值               | 建议深化                  |
| ------------------ | ----------------------- | --------------------- |
| Execution Swimlane | 同轴比较、异常聚焦、原始事件核查        | 加入事件依赖语义、跨阶段追踪、结论证据等级 |
| Layer Stack        | 多尺度认知、对象身份连续、局部数据检查     | 补充跨层映射规则、对象持久选择、计算关系  |
| Scale              | 参数共享、关联输出、用户介入、Agent 交接 | 增加修改前后 Diff、验证结果及证据状态 |

三个案例可以承担不同的方法论验证目标：

- Execution Swimlane 验证 行为与证据。
- Layer Stack 验证 对象与关系。
- Scale 验证 决策与干预。

这样能够用现有资产覆盖五层方法论，无需为了完整性再制作五个独立 Demo。

## 六、对图元—Pattern—框架—Skill 体系的建议

你当前这一部分的基础结构是合理的，不建议额外增加一层新的 UI 组件体系。

建议强化每层的职责：

| 层级        | 现有定位            | 应补充的设计约束                  |
| --------- | --------------- | ------------------------- |
| Glyph     | 规定对象的视觉语义       | 对象类型、状态、身份、尺度             |
| Pattern   | 规定对象关系与联动       | 适用问题、关系语义、时间语义、数据要求       |
| Framework | 规定调查空间          | 全局上下文、局部展开、跨视图连续性         |
| Skill     | 约束 Agent 的生成与核查 | 问题分析、Pattern 选择、证据检查、交付验收 |

最关键的是让 Skill 真正执行以下流程：

Engineering Visualization Workflow

1. 识别开发者需要回答的工程问题
2. 确认涉及的工程对象、关系及可用数据
3. 判断所需的空间、时间、数量及证据表达
4. 从已有 Glyph、Pattern、Framework 选择最小充分组合
5. 检查语义、数据绑定、跨层联动和证据来源
6. 通过真实工程任务验证认知与决策效率

其中第 3 步应该是新增的重点：让 Agent 学会选择为什么可视化、可视化什么，以及何时不需要可视化。

## 七、建议的修改优先级

P0

先完善方法论与生成约束

建立 Visualization Decision Matrix、跨层对象映射规则和 Evidence Model。这三项决定体系能否稳定迁移到新的工程问题。

P1

再完善动态 Pattern 和决策闭环

扩展 Memory Lifecycle、State Transition、Validation Compare，优先复用目前的三个案例。

P2

最后扩展到训练、推理和跨场景应用

用同一套对象与关系建模方法处理 Rank、Collective、Request、KV Cache、Expert 等对象，验证方法论的领域可迁移性。

## 最终建议

我认为目前不需要推翻你的理论架构，也不需要将三原则扩展成五原则。

更合理的是形成三层体系：

设计理念：聚焦、理解、介入。

设计方法：对象、关系、行为、证据、决策。

设计实现：Glyph、Pattern、Framework、Skill。

这三层分别回答了「为什么设计」「如何推导设计」「如何复用与交付设计」。

你的体系目前在设计理念和视觉案例上已经有了明确表达，下一阶段最有价值的工作，是把隐藏在案例中的专业判断沉淀为可复用、可检查、可被 Agent 执行的工程视觉设计规则。
