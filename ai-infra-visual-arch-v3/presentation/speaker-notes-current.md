## P01 · 设计依据与工程前提

来源：`./pages/01-domain-theory.md`

想象一根下载进度条，你脑中这个进度条是很顺利地加载完了，还是卡在某个点不动了？

我们作为 C 端用户，看到进度条卡住都很习以为常了。是不是网络不好？或者这个进度条是不是“骗人的”？

计算领域的开发者，其实也会面对这样一根进度条。一个计算任务跑到哪里了，为什么这里特别慢？但这根进度条背后，需要打开的黑盒就多得多了。我们归纳了三个方面。

领域知识。

计算机制。

人的认知。

Agent 的工程能力。 在今天这个 AI 时代，开发者看到任务卡住，第一反应可能是派一个 Agent 去调查。但 Agent 需要具备领域知识、工具调用、证据管理和执行验证能力，才能将开发者的问题转化为持续推进的调查任务。

我们的设计工作建立在这些工程能力之上，结合前面三个方面，重点研究如何把 Agent 组织的复杂证据，转化为开发者能够理解、核查和介入的交互体验，帮助他依据证据作出决策。

## P02 · 【领域知识】多对象、跨层级与语义关系

来源：`./pages/09-knowledge.md`

不管是开发一个小算子，还是让一个 DeepSeek 这样的大模型跑起来，背后都涉及大量专业知识。过去，开发者需要学透这些类目，凭经验把这些知识关联起来，才能理解计算过程发生了什么。

对设计师来说，我们也需要从这些领域知识入手，梳理计算中有哪些基本对象、层级和关系，思考如何把它们转化为一套可复用的视觉积木。

## P03 · 【计算机制】从执行依赖理解运行行为

来源：`./pages/10-computation.md`

同样是“这里耗时特别长”，究竟是在等待内存数据搬运，还是存在资源争用？这涉及计算、访存、通信、同步和资源调度等硬件与执行约束，需要结合运行证据进一步判断。

现在计算开发的一个趋势是，上层计算逻辑越来越抽象，底层执行和硬件资源的关系却越来越复杂。开发者即使理解了计算逻辑，也不容易直接判断它在硬件上如何执行，以及性能差异究竟来自哪里。

## P04 · 【认知机制】从人的视知觉理解复杂计算

来源：`./pages/11-visual-cognition-foundation.md`

前面讲了计算领域的复杂性。对设计师来说，问题不只是界面够不够美观、功能够不够完善，而是这些复杂关系有没有符合人的基本认知方式。

我们可以借鉴一些成熟的视觉感知规律。比如人擅长通过空间位置和分组理解结构，通过形状和差异识别对象，通过变化感知理解动态过程。

结合计算领域的特点，我们可以把这些规律转化为具体的视觉表达，让开发者能够在同一个视觉空间中，理解原本需要在代码、日志和指标之间反复切换才能建立的关系。

最终，我们希望形成一套**明晰、连贯、可控**的视觉表达，并以此作为计算领域视觉设计的基础体验标准。

## P06 · 【认知机制】Transformer 图元设计案例 · 步骤 1

来源：`./pages/13-cognition-case-1.md`

接下来以 Transformer 计算图为例，看看这些认知规律怎样转化为具体设计。

怎么表达Tensor数据？统一网格形态帮助识别对象类别；颜色辅助区分激活、中间值和权重等角色，文字补充明确角色与 Shape，避免只靠颜色辨认。

计算节点OP和数据如何最大化区分？我们用胶囊形态与 Tensor 的网格形成明显区分，同类 OP 保持一致的视觉规则，再通过图标和名称识别具体计算操作。

第三步组织计算关系。我们用容器表达子层的归属关系，通过主干和旁路区分主要数据流与分支，让开发者能够沿着计算路径理解整个结构。

第四步我们想表达空间中模型层的连续，单个 Transformer Layer 只是模型的一部分，我们通过空间上的连续排列，表达多个 Layer 之间的顺序与连接，让开发者从局部计算关系回到模型整体。

这四步实际上是一个从对象识别、关系组织到整体空间理解的设计过程。随着观察尺度变化，表达的细节可以不同，但对象身份和计算关系需要保持连续。

## P10 · 三项设计原则 · 步骤 1

来源：`./pages/03-language-0.md`

到目前为止，初步定义了表达计算关系的视觉语言，只要agent拿到样例和设计规则它其实能无限繁衍出图元，但是形成一个真正有价值的设计还需要从体验层面去思考决定开发者看什么、看多深，以及如何参与。

围绕这三个问题，我归纳了三个设计原则：证据驱动、认知减负、协同控制。

第一个是证据驱动。开发者现在需要看什么？

可以是一次运行的报错、关键异常点，甚至是 Agent 初步排查后一些值得关注的检查点。

第二个是认知减负。这些信息，一次需要看多少？

这也是设计师很熟悉的信息层级和渐进披露。和 2.0 相比，新的体验理念共识在于不是所有场景都需要复杂可视化。一个摘要就能回答的问题，我们就先给摘要。需要比较多个对象时，再展开它们的关系。需要深入调查时，再进入细节。

从整体进入局部的过程中，要让他始终知道自己在看哪里、当前选中了什么。

第三个是协同控制。看完以后，开发者能做什么？

我们做可用性设计时，会考虑反馈是否清楚、操作是否可控，以及出现问题后能不能纠正。到了 Agent 协同的场景，这些要求仍然成立。Agent 给出了一个解释，开发者需要能检查它的依据。觉得某个条件有问题，需要能调整参数、看看影响。有了新的判断，还需要把当前对象、条件和证据一起交回 Agent，让它接着调查。这样，开发者的判断才能真正介入，而不是靠盲调代码或者和 AI 无休止对话。

## P16 · 三钻协同方法

来源：`./pages/03-collaboration-method.md`

前面提出的三项设计原则，不只是指导设计师如何组织信息，也可以进一步指导开发者与 Agent 如何协同完成任务。基于这个思路，我尝试提出一个三钻模型，对 AI 计算开发中的人机协同体验做一个初步探索。三个阶段分别是聚焦问题、理解证据、介入并验证，每个阶段都有人和 Agent 的分工，以及明确的协同产出。

这不是一次走到底的流水线。理解时发现调查范围不对或证据不足，就返回 Focus 修订调查任务；介入或验证时发现解释不充分、结果不符合预期，就返回 Uncover 核查依据。每次返回都保留对象、条件和证据。

接下来通过三个具体案例，分别看看在聚焦、理解和介入阶段，我们可以怎样设计视觉表达与交互。

## P17 · Focus · 执行泳道 · 章节开场

来源：`./pages/04-attention-cover.md`

第一个阶段是 Focus，聚焦问题。比如开发者发现这次运行特别慢，Agent 可能已经找到了很多线索，但究竟哪里值得优先调查？这时候人和 Agent 需要一起缩小范围，先找到最值得关注的问题。

之前 2.0 的泳道界面里有非常密集的任务条、颜色和文字标签。它们提供了丰富的执行信息，但当开发者带着一个具体问题进来，比如“这次运行为什么慢”，还是需要自己从里面寻找、比较。

所以我想做的是，围绕当前问题建立视觉层级，让值得关注的差异更容易被看到。

首先，总览的认知负担减轻了很多。这里可以看到，第 6 条泳道最晚进入运行阶段。

这里展示的是 Host 端的调用记录。

顺着这个差异往下看，当前这组记录的 54 个步骤中，它有 53 次都是最晚进入的，所以值得继续调查。

回到开场的进度条，这些记录能帮助我们发现哪一路进得晚，给后续调查一个起点。

## P24 · Uncover · Layer Stack · 章节开场

来源：`./pages/05-layers-cover.md`

第二个阶段是 Uncover，理解证据。找到值得调查的问题之后，还需要理解它背后的计算关系。Agent 可以帮助关联证据，但开发者怎么才能看懂这些关系呢？

我们之前采访发现，很多开发者其实只熟悉自己负责的算子部分，对整个模型的上下游缺乏贯穿的认知。

所以这里的设计重点，是让开发者能够从整个模型，一直深入到具体计算节点和数据，同时不丢失自己的位置。

首先看到的是模型的 49 层结构。远的时候先看整体层序，近一点看到第 18 层内部的计算关系，再深入到 Query 对应的数据。

这里展示的是一个 64×64 的局部采样。即使进入具体数据，也能知道它属于哪一层、哪个节点，以及当前的采样位置。

这个案例体现的就是我们熟悉的渐进披露，加上计算领域特别需要的跨层级对象关联和上下文保持

## P31 · Intervene · Scale · 章节开场

来源：`./pages/06-agent-cover.md`

第三个阶段是 Intervene，介入并验证。当开发者理解了计算关系，能不能直接在视图里核查，甚至调整条件，再让 Agent 继续调查？

接下来这个案例就用一个比较简单的计算 OP，说明开发者怎么参与核查。这里是一个 Scale 计算，可以简单理解为输入乘以一个倍率。这个例子里，两批输入共用了同一个倍率。

首先选中这个参数，画面会把它影响的输出标出来。这样开发者在修改之前，就能先看清影响范围。

接着，把倍率从 −1 改成 1，可以看到两批对应的输出都发生了变化，看看变化是不是符合预期。

如果开发者仍然觉得参数共享关系有问题，就可以把当前对象、参数和计算依据整理成上下文，交回 Agent 继续调查。

目前这个原型已经实现了参数联动、算式核查和上下文整理，后续 Agent 自动接续调查和修复，是希望进一步接通的能力。

## P38 · 设计资产与 Skill · 章节开场

来源：`./pages/07-system-cover.md`

一个agent怎么才能稳定有效能输出前面案例这样的可视化工具呢？这就需要把设计经验沉淀成代码和能力并且不断地自我迭代。

这里我们组有同学在研究上层的 Agent Harness，负责规划调查、调用工具和执行验证。我主要负责下面的设计层，通过 Design Skills 和 MCP，让 Agent 能够根据当前问题和证据，选择、组装并核查可视化表达。

具体沉淀为三类资产。

首先是**图元**，统一 Tensor、OP、Memory 等计算对象的视觉语义，让不同场景保持一致。

其次是 **Pattern**，把执行泳道、模型层级、参数联动等关系表达沉淀下来，让 Agent 根据问题选择合适的可视化方式。

最后是**交互框架**，统一画布、导航和核查面板，让复杂关系能够在同一个工作空间里逐步展开。这用一个内存案例，看看这些设计怎么用框架组合起来。

画布中展示了某个pass把四路绑定指向同一个内存地址，agent检查发现了问题和证据呈现在核查面板中，但是可视化本身还不足以给出解决方案，继续调查就是harness需要衔接的能力了，比如接入业务开发的一些cannbot skills，就能进一步实现校错调优。

这也对应了 Skill 的工作流程。先明确工程问题和现有证据，再决定需要表达什么关系，组合已有的图元、Pattern 和框架，最后核查对象绑定、交互和来源。

## P43 · 总体架构

来源：`./pages/08-summary.md`

最后，我把前面所有的研究和设计工作整理成了这张总体架构。

最上面是我们的体验目标：从传统计算领域的信息组织与呈现，转向复杂计算系统的认知与决策辅助。

围绕这个目标，我们从领域知识、计算机制和人的认知出发，提出证据驱动、认知减负和协同控制三项原则。

再通过三钻模型，把这些原则应用到开发者与 Agent 的协同过程，去指导agent更好辅助开发者聚焦问题、理解证据，并在关键节点介入和验证。

最后是落地层。我们把领域知识沉淀为设计逻辑，把图元、Pattern 和交互框架沉淀为视觉资产，再通过 Skill 与 Agent 的工程能力衔接，让这些设计能够被持续复用。
