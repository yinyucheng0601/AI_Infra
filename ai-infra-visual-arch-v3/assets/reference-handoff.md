
可观测和可视化设计在用户使用ai agent的主流开发的条件下有什么变化？目前可观测和可视化的UXUI，从人性角度，需要关注哪类问题才有价值？
AI Agent 成为主流开发方式后，可观测性与可视化 UX/UI 应该如何变化？
我的核心判断是：当 AI Agent 成为开发者的主要执行者时，可观测性与可视化的价值，不再主要是“让人看见系统内部发生了什么”，而是“帮助人判断 Agent 做得对不对、问题出在哪里、是否值得信任，以及何时需要介入”。

这不是说传统的指标、调用链、计算图、IR、编译 Pass 等可视化不再重要，而是它们的角色发生了变化：从开发者主动探索的主界面，逐渐转变为 Agent 推理、验证、解释和纠错所调用的证据与交互界面。

但需要区分两件事：

可观测性（Observability）：系统是否产生了足够的证据，让人或 Agent 能够判断内部状态、识别异常并定位原因。

可视化（Visualization）：如何把这些证据组织成人能够理解、比较、判断和采取行动的表达形式。

两者并不等价。一个漂亮的仪表盘可能缺少根因证据；一个没有复杂图表的诊断结果，也可能足以让开发者做出正确决策。

一、从 Human-driven Development 到 Agent-driven Development，发生了什么变化？
传统开发
人主动探索系统
人提出假设 → 打开工具 → 查看指标与日志 → 沿调用链排查 → 判断原因 → 修改代码

UX/UI 的主要任务：降低查找、导航、关联和理解系统状态的成本。
Agent 参与或主导开发
人定义目标，Agent 执行与诊断
人描述问题 → Agent 规划并执行 → 收集证据 → 形成诊断 → 尝试修复 → 验证结果 → 人审核或介入

UX/UI 的主要任务：让执行过程可验证、诊断有证据、变更可控、失败可恢复，并让人能在关键节点做出正确判断。
这意味着 UX/UI 设计的重心应从“信息展示效率”扩展到“人机协作的决策质量”。

这里最重要的区别是：Agent 能够调用某个工具，不代表它能够正确理解工具的结果；Agent 能够生成一个看起来合理的解释，也不代表这个解释已经被验证。

因此，未来可观测性设计必须同时服务于机器诊断与人类判断，而不能只优化其中一方。

二、从人的角度看，最值得解决的不是“看不见”，而是六类问题
如果从人因、认知心理学和人机交互的角度重新审视可观测性 UX/UI，我建议不要先从图表类型、布局或组件出发，而是从人在使用 Agent 时承担的认知任务和风险出发。

1. 认知负担：我需要自己理解多少？
人的注意力和工作记忆有限。Agent 可以一次执行大量工具调用、读取大量文件、遍历复杂计算图，但不能把这些原始信息全部塞回给人。

有价值的设计： 先呈现问题结论、关键证据、影响范围和下一步行动；允许用户沿着证据逐层深入。让人从“浏览所有信息”转向“审查关键判断”。

应该避免： 把所有 Trace、日志、指标和内部状态堆进一个综合大屏，要求人自行拼出根因。

2. 信任校准：我为什么应该相信 Agent？
人既可能过度相信流畅、确定的解释，也可能因为一次失败就不再信任系统。真正需要的不是让界面“看起来更智能”，而是让结论的可信程度能够被检验。

有价值的设计： 区分已观测事实、推断出的原因、尚未验证的假设；展示证据来源、对照结果、反例和验证状态。

应该避免： 仅给出一个根因标签、一个置信度百分比，或一段无法追溯证据的自然语言解释。

3. 控制感与自主权：我还能决定什么？
Agent 的自主性越高，人越不应该被迫逐条批准无风险的小操作，也越不能在关键操作上失去控制权。

有价值的设计： 提供暂停、终止、纠正方向、限制权限、撤销变更和恢复现场的能力；根据风险、可逆性和不确定性决定何时需要人工确认。

应该避免： 两个极端——所有动作都要求批准，或 Agent 一路执行到底，只在最后展示结果。

4. 情境理解：问题究竟发生在哪里？
人需要把抽象异常映射到自己熟悉的业务对象、代码、执行阶段和影响范围。一个指标异常本身通常不是完整的解释。

有价值的设计： 把异常与具体任务、代码版本、输入条件、执行路径、资源、对象关系及历史基线关联起来，让用户知道“哪里发生变化、变化影响谁、为什么值得关注”。

应该避免： 只突出红色告警，却没有提供从症状到具体对象的关联路径。

5. 可验证性：怎样知道问题真的解决了？
Agent 完成了任务、测试通过了、性能变好了，是三个不同的判断。人需要能够区分“执行完成”与“目标达成”。

有价值的设计： 让修复前后使用相同的输入、基线、指标和约束进行比较，展示回归测试、残余风险和未覆盖的条件。

应该避免： 只显示“Success”，或把局部测试通过直接解释为系统整体正确。

6. 可恢复性与责任：失败后我能否接管？
Agent 可能走错方向、反复尝试、修改错误文件，或在不完整信息下继续执行。对用户而言，错误之后的恢复能力往往比理想情况下的成功路径更重要。

有价值的设计： 保存关键执行记录、代码与配置差异、操作影响范围、检查点和恢复路径；明确谁批准了什么，以及失败时处于什么状态。

应该避免： 只有一条线性的成功流程，失败后却无法还原 Agent 做过什么。

为什么这些问题不是纯粹的设计假设？
Anthropic 对 Claude Code 使用行为的研究发现，随着用户经验增长，用户更倾向于自动批准操作，同时也会更频繁地中断 Agent；复杂任务中，Agent 主动请求澄清的频率超过了用户主动打断的频率两倍。其结论之一是，监督应更注重用户能否有效观察和介入，而不是强制每一步都由人批准。

不是让人持续盯着 Agent，而是让人能在需要时及时看懂、介入和纠正 Agent。

三、可观测性与可视化的设计目标，应该怎样重新定义？
我建议把两者分成三个层次，避免将所有需求都归结为“需要更多图表”。

第一层：可观测性基础设施
回答：有没有足够证据还原实际发生的事情？

任务、Agent、工具调用和外部系统之间的关联

输入、输出、状态变化、错误和时间信息

代码、配置、模型、运行环境和版本

权限、审批、重试、记忆变化和操作结果

基线、测试结果及可复现的执行条件

第二层：可视化与解释
回答：这些证据意味着什么？

识别异常、变化点和影响范围

将指标映射到对象、执行阶段和依赖关系

展示证据链、竞争性假设与不确定性

对比基线与当前状态、修复前与修复后

根据用户的专业水平组织信息层级

第三层：人机协作与行动
回答：现在应该做什么，谁来决定？

继续诊断、执行修复或补充证据

请求人工判断、批准或改变目标

限制操作范围、暂停执行、回滚变更

验证修复是否满足预定约束

沉淀人工纠正与失败案例，改善后续诊断

这三个层次相互依赖，但不能互相替代。

例如，Agent 给出“内存带宽不足”的诊断，属于解释层；如果没有设备侧计数器和运行记录支撑，就可能只是猜测。即使证据充分，如果界面不允许用户对比相关 Kernel、检查访存布局或验证修复，也还没有完成从可观测到可行动的闭环。

当前的产业实践也在向这个方向演进：Google Cloud 的 Agent 可观测性文档将工具调用、模型交互、执行 Trace、延迟、Token 用量和输出质量纳入观测范围；Microsoft 的相关指南则强调，非确定性行为意味着传统的延迟、错误率和吞吐量不足以完整判断 AI 系统的可靠性。

因此，可观测性不应只回答“系统运行得怎么样”，还应回答“Agent 是否可靠地完成了任务，以及这个判断有何证据”。

四、具体到 UX/UI，哪些设计最有价值？
下面是我认为值得优先投入的八类设计能力。这里的优先级是基于人因、诊断价值和工程风险的设计判断，不是声称已经通过统一实验得出的行业排名。

UX/UI 能力

有价值的设计产物

风险提示、暂停、审批、方向修正

高复杂度、高不确定性的问题：需要可探索的诊断界面

例如精度回归、编译 Pass 改变计算语义、并行通信错误。用户需要沿着证据链从模型级症状深入到算子、IR、内存布局或硬件执行，再对比候选原因并验证修复。

这意味着设计不应该追求“所有问题都使用同一种仪表盘”，而应采用由问题复杂度和决策风险决定的信息表达方式。

五、结合 AI Infra、算子开发与训练推理：一个具体例子
假设开发者让 Agent 排查一个昇腾算子优化后出现的精度异常。

传统工具可能展示各阶段 RMS 误差、编译日志、IR、计算图和设备指标。Agent 开发模式下，更合理的体验可以是：

1. 先回答用户的问题
问题：优化后精度为什么退化？

诊断摘要：误差在 Reduction / Fusion 阶段首次明显增大，后续阶段未显示同量级新增误差。

以上为示例场景，不代表真实设备测量结果。

2. 显示可验证的证据
以一致的输入、参考实现和误差定义比较各编译阶段。

Mock 数据；误差指标与比较口径必须在真实产品中明确定义。

3. 将异常定位转化为可检验的假设
Reduction 顺序是否改变？

累加精度或 Cast 位置是否改变？

Fusion 是否改变了数值计算路径？

每项假设都需要相应的 IR Diff、编译配置、阶段输出或独立复现结果。仅凭误差首次出现的位置，还不能认定具体根因。

4. 提供修复与验证闭环
展示候选修复、代码差异、性能影响和精度回归结果。由用户决定是否采纳高影响变更；如果证据不足，继续采集信息，而不是直接宣布根因已确定。
在这个例子里，图表只是辅助。真正有价值的体验是把用户从“我看到精度异常”带到“我知道应该检查什么、为什么检查、如何证伪、怎样确认修复有效”。

这也解释了为什么 Agent 开发并不必然降低 IR、Pass 或计算图可视化的价值。它可能减少人手动浏览这些信息的频率，却会提高这些信息在关键诊断时刻作为可验证证据的价值。

七、如果要评估一个可观测性产品是否真正有价值，应该看什么？
我建议将评估从传统的“功能是否齐全、指标是否丰富、图表是否美观”扩展到以下结果指标。

建议优先验证的 UX 指标
诊断效率

从症状出现到定位可验证原因的时间；用户需要手动查找多少信息。

诊断正确性

根因判断是否被独立测试、复现或专家审查证实；是否能识别错误假设。

信任校准

用户能否区分已验证结论与推断，是否会发现并纠正 Agent 的错误判断。

介入有效性

用户能否在关键风险发生前介入，介入是否有效，以及是否减少了不必要的审批。

修复闭环质量

修复后的回归率、验证覆盖率、恢复时间，以及是否产生新的性能或正确性问题。

这些指标应当结合具体任务建立基线，通过用户测试、故障注入、真实案例回放和线上数据验证。不能仅凭用户停留时间更长、点击更多图表或对界面的主观满意度，就认定可观测性设计更好。

八、最终建议：把可观测性 UX/UI 设计成“人类决策支持系统”
我会用下面这个框架来决定一个功能是否值得做：

一个可操作的价值判断框架
1. 人遇到了什么决策困难？

看不到问题、理解不了关系、无法判断证据，还是无法安全介入？

2. Agent 是否能可靠地完成这一步？

如果能，界面是否只需提供结果摘要和必要证据？如果不能，缺少什么数据、工具或验证机制？

3. 人需要看到什么，才能做出更好的判断？

选择摘要、时间线、关系图、Diff、矩阵或可交互诊断视图，而不是先选图表类型。

4. 如果判断错了，能否发现、介入和恢复？

确认操作权限、风险提示、证据追溯、回滚能力和验证结果。

5. 怎样证明这项设计有价值？

比较诊断时间、正确率、人工介入质量、误判率与修复后的回归风险。

我的最终判断是：

在 Agent 主导开发的环境下，可观测性仍然负责让系统变得可诊断；可视化仍然负责把复杂状态转化为人可以理解的表达。但 UX/UI 的核心竞争力正在转向三个更根本的问题：

认知减负：让人不必理解所有细节，也能理解最关键的问题。

信任校准：让人知道 Agent 的结论何时可靠、何时还需要证据。

有效控制：让人能够在关键时刻纠正、拒绝、恢复和验证 Agent 的行动。

对 AI Infra、算子编译和训练推理工具而言，这意味着不必把每个内部对象都做成一个独立可视化页面。更值得投入的是：让 Agent 能够调用正确的观测能力，并把真正影响开发者决策的证据组织成可理解、可追溯、可验证、可行动的界面。

换句话说，好的 Agent 时代可观测性 UX/UI，不是让用户看得更多，而是让用户用更少的注意力，做出更正确的判断，同时不失去对系统的控制。

八、什么不值得优先做成可视化？
为了避免过度建设，我建议明确排除三类低优先级需求。

1. Agent 已经能够可靠回答的简单问题

例如参数名拼写错误、依赖缺失、明确的编译错误。只要错误信息、修复差异和验证结果足够清晰，就不需要强制展示复杂图表。

2. 没有对应诊断任务的内部对象展示

不应因为系统存在 IR、Pass、Tensor、Rank、Kernel 或硬件计数器，就默认每个对象都需要独立页面。只有当它能帮助区分候选原因、验证假设或支持关键决策时，才值得作为主要交互。

3. 不能连接到行动的纯状态大屏

如果用户看到异常后仍然必须离开页面，自己搜索日志、找代码、重新运行测试才能继续，说明可视化没有形成完整的诊断路径。

一、先明确要验证的产品假设
我建议把本次验证定义为一项对照实验，而不是先做一个完整的可观测性平台。

核心问题是：

当 CLI Agent 已经能够编写代码、运行编译、测试和 Profiling 时，额外提供一套按诊断任务组织的可视化界面，是否比纯 CLI 输出、日志和 Agent 自然语言总结更有效地帮助开发者定位问题？

这项实验尤其要区分三个不同的结果：

Agent 自己已经能解决的问题：可视化可能没有增量价值。

Agent 能发现异常，但无法可靠解释根因的问题：可视化可能帮助人检查证据、纠正判断。

Agent 和人都难以处理的跨层问题：可视化可能通过关联不同证据显著降低定位成本。

首要评价指标是从开始排查到找到经过验证的根因所需的时间，而不是用户打开了多少图表、Agent 调用了多少工具。

1.1 研究问题与待验证假设
H1 · 核心假设
证据关联视图能缩短根因定位时间。

在相同 Agent、工具权限、诊断数据和问题难度下，提供可视化证据链的组，比仅使用 CLI / 日志 / 自然语言总结的组，更快找到经过独立验证的根因。

H2 · 机制假设
收益主要来自减少跨工具、跨阶段的信息关联成本。

例如将精度误差、编译 Pass、IR 差异和运行结果关联起来，比单纯把日志改成图表更有价值。

H3 · 适用范围假设
可视化的收益与问题类型有关。

简单的语法或参数错误可能不需要可视化；跨编译阶段、数值精度和硬件执行的问题可能更受益。

H4 · 人机协作假设
证据可追溯性比单独展示 Agent 的根因结论更能帮助用户判断。

用户应该能够查看支持证据、发现反例，并在证据不足时拒绝 Agent 的结论。

以上均是需要通过实验验证的假设，不是已被当前讨论证明的结论。

二、实验范围：先选什么问题，才有可能得到可信结果？
建议首轮实验聚焦于单个算子、单次编译与运行、可以复现并且有明确根因判定标准的问题。不要一开始就覆盖整个模型训练、分布式执行和所有硬件问题，否则难以判断可视化究竟在哪一步产生价值。

首轮可以使用真实缺陷复现，也可以使用从真实问题中构造的受控变体。必须明确区分两者，不能把 Mock 指标当作真实故障证据。

3.2 建立可审核的根因真值
每个案例由不参与界面设计的领域专家预先建立根因判定记录，至少包括：

根因定义： 能够精确描述的缺陷或机制，而不是“精度异常”“性能不足”这样的症状。

复现条件： 源码版本、编译配置、输入、运行环境和触发条件。

验证方式： 通过对照实验、最小复现、边界测试或受控变更，证明根因与问题之间的关系。

修复验证： 证明修复消除了目标问题，同时检查没有引入新的正确性问题。

允许的等价答案： 多个根因描述或诊断路径何时可视为正确。

证据边界： 哪些结论已经确认，哪些只能作为候选解释。

对于存在多个共同原因的案例，应当预先定义可以接受的根因集合与验证条件，不能强迫专家给出一个虚假的唯一答案。

5.1 必须控制的 Agent 行为
为了让实验结果可比较，建议为所有实验条件固定：

相同的 Agent 模型、版本、系统提示和工具权限。

相同的源码、配置、测试、日志和诊断工具。

相同的最大执行预算，例如工具调用次数或执行时间。

相同的自动修复权限与人工审批规则。

相同的根因验收标准。

如果某组 Agent 可以调用额外工具、拥有更多上下文或运行更多实验，就不能把性能差异单独归因于可视化。

5.2 不应该让 Agent 自己证明自己正确
Agent 可以提交根因解释和验证结果，但最终评分应由预先定义的判定规则、自动化测试和独立评审共同完成。

特别是精度问题，不能只看 Agent 生成的文字是否与专家答案相似。还应验证它是否正确识别误差来源、是否有支持证据、是否能在受控变更后复现预期结果。

六、对照实验：怎样证明可视化真的缩短了定位时间？
建议分成两个阶段：先做小规模可用性试点，再开展正式的对照实验。

6.1 三组实验设计
A 组
CLI 基线组
Agent + CLI + 原始日志与测试输出

使用现有的命令行工作流、编译器输出、测试结果和 Agent 自然语言总结。不提供新的专用诊断界面。

B 组
结构化摘要组
Agent + CLI + 结构化诊断摘要

在 A 组基础上，增加统一的阶段状态、异常摘要、根因候选、证据链接和下一步建议，但不提供专门的关系图或交互式诊断图表。

这组用于区分“信息整理更好”的收益与“图形化表达”的额外收益。

C 组
可视化证据组
Agent + CLI + 结构化摘要 + 交互式诊断视图

在 B 组基础上增加按问题类型选择的误差对比、编译变换 Diff、性能时间线或 Tile / Block 映射，并支持查看原始证据、修正假设和发起验证。

三个组的对比可以分别回答：

C vs A：完整的可视化诊断方案是否优于现有 CLI 工作流？

B vs A：结构化摘要和证据整理本身是否已经足够？

C vs B：交互式可视化是否带来了额外价值？

这三个比较不能互相替代。 如果 B 组与 C 组效果相近，说明真正的收益可能来自证据整理，而不是复杂图形；如果只有 C 组明显改善跨阶段问题，才更支持建设专用可视化组件。

6.2 实验流程
准备与校验案例。 专家确认根因真值、复现脚本、输入条件、验收测试及各组都能获取的数据。

进行小规模试点。 让 3–5 位有相关经验的开发者检查任务说明、工具可用性、记录机制和评分规则。此阶段只用于发现流程缺陷，不作为正式显著性结论。

按经验分层招募参与者。 尽量覆盖熟悉该编译器的专家和一般算子开发者，记录实际相关经验，而不是只记录总工作年限。

随机分配实验条件与任务顺序。 采用平衡的任务顺序，避免同一参与者先学会某个案例后直接把答案带入另一个实验条件。对于可能产生明显学习效应的重复案例，应使用等价但不同的缺陷变体。

执行诊断任务。 参与者使用对应工作流独立排查，记录 Agent 工具调用、界面交互、时间、假设变化和最终结论。

独立评分与复核。 由不知道参与者实验分组的评审依据预设规则判定根因是否正确、证据是否充分，以及修复是否通过验收。

分析结果并复测。 先比较定位时间与正确率，再分析哪些任务类型、经验水平和界面能力解释了差异。必要时扩大样本进行确认性实验。

6.3 样本量怎么确定？
不要先拍板“10 个人就够”或“30 个人一定有效”。样本量应当根据试点中观察到的时间差异、参与者间变异、案例难度和预先定义的最小有意义改善幅度来计算。

建议：

试点阶段：3–5 位开发者，主要用于检查流程和估计变异。

正式阶段：先用试点数据估计所需样本量，再决定参与者人数和每人的任务数。

如果参与者需要重复完成多项任务，分析时要考虑同一参与者的相关性，以及任务难度差异；不能把每次任务都简单当作独立样本。

如果样本不足以得出稳定结论，应报告效应大小与不确定区间，而不是只报告一个显著性结论。

如果需要进行正式统计检验，建议预先注册主要指标、排除规则、比较方法和成功标准，避免看到结果后再挑选最有利的指标。

九、落地计划：四周完成一个可评估的原型
第 1 周
案例与基线

收集真实缺陷、建立根因真值、固定 CLI Agent 和工具配置；完成首批案例的复现和评分规则。

第 2 周
原型与埋点

实现 CLI 执行记录、诊断摘要、精度对比视图和证据追溯；先做任务 A 的端到端流程。

第 3 周
小规模试点

邀请 3–5 位开发者试用，检查任务是否可理解、数据是否可用、证据是否可追溯、记录是否完整，并修正实验流程。

第 4 周
对照实验与决策

在资源允许时开展正式对照；如果样本量不足，则完成先导实验、估计效应和变异，并据此制定后续确认性实验。

四周适合作为一个可执行的原型周期，但正式对照实验是否能在四周内完成，取决于参与者招募、真实案例数量和样本量要求。

最终交付物
案例库： 问题定义、复现环境、根因真值、验证步骤及数据可用性说明。

可运行原型： CLI 执行记录、诊断摘要、精度证据视图和可追溯的验证流程。

实验记录系统： 自动记录任务时间、工具调用、界面交互、人工纠正与最终结果。

对照实验报告： 主要指标、正确率护栏、任务分类结果、效应大小与不确定性。

产品决策建议： 明确哪些诊断视图值得建设、哪些问题用结构化文本已经足够、哪些数据源还不具备落地条件。

十、最终建议
我建议把第一阶段的范围收敛为：

CLI Agent + 算子精度异常 + 结构化证据链 + 交互式阶段误差视图。

先比较三种体验：纯 CLI、结构化诊断摘要、结构化摘要加可视化。通过独立根因判定，检验专用可视化是否真正缩短正确定位时间。

如果结果显示 C 组优于 B 组，且没有损害诊断正确率，再扩展到编译 Pass 追溯、性能归因和尾块 / 内存问题。若 B 组已经获得相同收益，则优先建设结构化证据协议，而不是继续增加图表。

这套方案的价值不在于预先假定可视化一定有用，而在于建立一个能够证明可视化何时有用、对谁有用、为什么有用，以及什么时候不值得做的验证机制。

这恰好补上了你之前希望建立的「AI 时代的 Perfetto」方向中，比较欠缺的一环：从可视化表达能力，走向 Agent 驱动的问题调查与人工决策支持。

一、原来的 Skill 目标与这次讨论的关系
结合我们之前讨论的 ai-infra-investigation、Design Spatial System，以及算子、训练和推理可视化，我建议这样理解它们的演进：

层次

原有目标

本轮讨论补充的目标

问题选择

根据技术主题生成相关图表

根据开发者的实际诊断任务，判断何时值得可视化

Agent 工作流

Agent 收集材料、分析并生成视图

Agent 自主处理常规问题，仅在关键判断节点调用可视化

证据约束

区分源码推导、编译产物与设备观测

明确每类问题的最低证据、允许结论及验证方法

可视化设计

统一图元、空间表达、布局、联动和交互

用证据关系、对照和局部展开降低人的诊断负担

人查看生成的分析结果

人检查证据、纠正 Agent 假设、控制参数并触发继续调查

结果验收

图表准确、易读、交互可用

验证是否缩短正确定位时间，同时控制误判风险

其中最重要的新目标是：可视化应当由具体的决策困难触发，而不是由数据类型或技术对象触发。

例如，编译器存在 30 个 Pass，并不意味着需要生成 30 个 Pass 视图。只有当 Agent 发现某个编译变换可能与误差或性能回归有关，而文本总结不足以让开发者可靠判断时，才应调用对应的 IR Diff、Tensor Mapping 或执行视图。

这会直接改变 Skill 的规划逻辑。

二、我建议补充 5 个核心能力，而不是再增加图表模板
1. Problem-driven Visualization：让 Skill 判断何时需要可视化
这是最高优先级。

之前的 Skill 更关注如何正确表达 Tensor、IR、内存、通信和执行时间线。现在应该增加一个前置决策：当前问题是否真的需要可视化，以及哪种表达最有助于判断？

建议在 Skill 中加入 Visualization Trigger 规则。

问题特征

Agent 默认处理

触发可视化的条件

直接可定位的错误

文本解释、代码修复、测试

默认不触发

多阶段精度异常

比较 Golden、误差分布

需要判断误差出现位置或数值传播关系

编译变换异常

分析 IR、Pass、源码

需要比较结构变化与语义关系

性能瓶颈

收集 Profiling 数据

需要分析时间重叠、资源竞争和瓶颈转移

尾块与访存异常

静态检查、边界测试

需要理解索引、Mask、Tile 与物理地址关系

根因存在多个候选

Agent 形成假设列表

需要人比较证据、排除假设或选择下一步实验

这个能力可以避免你之前担心的问题：Agent 给每个 Shape、Pass、Core 生成大量图表，导致开发者不得不逐个浏览。

2. Evidence Contract：为每类问题规定证据契约
之前我们讨论过，你领导希望 Skill 对证据获取、结论准确度和信息量有更严格的约束。

本轮讨论可以把这个要求落成明确、可检查的规则。

例如对于算子精度异常：

内容

Skill 应有的约束

最低输入

源码版本、Shape / dtype、参考输出、实际输出和容差

可提出的结论

哪些输入出现误差、误差分布、候选异常阶段

更强结论所需证据

阶段输出、IR 对照、受控复现或独立验证

不允许的跨越

仅凭最终误差断言某个 Pass 是根因

缺失证据时

标明待验证项，并给出下一步采集命令

输出控制

优先显示异常阶段及其关联对象，其余细节按需展开

尤其应延续你之前明确的要求：不能把源码推导的逻辑布局当成编译后分配地址，也不能把估算时长当成设备真实测量。

Skill 不应该只告诉 Agent 如何画图，还应该限制它能够依据什么证据作出什么结论。

3. Agent–Human Handoff：定义人工介入时机
之前 Skill 的主要产物是生成的图表或页面。现在可以补充一个概念：Decision Checkpoint（决策检查点）。

Agent 自动调查

执行测试 → 收集证据 → 提出候选原因 → 确定下一步诊断价值

触发 Decision Checkpoint

例如存在两个有证据支持、但需要不同验证实验的根因假设。

用户看到

当前结论、支持证据、关键差异、未验证部分和下一步选择。

接受并继续
调整参数
否定假设
查看原始证据
Agent 根据反馈继续

执行对照测试 → 验证假设 → 更新证据与结论 → 形成可追溯结果

这比单纯提供一套交互图表更符合你设想的开发方式：开发者主要在 CLI 中与 Agent 协作，只在关键环节打开可视化，把控诊断方向，不需要学习另一套复杂的独立工具。

而且人工介入应该由决策风险、证据冲突和可逆性决定，而不是每次 Agent 生成图表都要求审批。

4. Diagnostic View Composition：以问题为中心组织视图
这是对原有 Design Spatial System 最直接的补充。

原先你已经在沉淀图元、Pattern、对象身份、空间布局、颜色契约和联动规则。这些可以继续保留，但应增加诊断级视图组合规则。

以精度异常为例，Skill 应能把以下元素组织为一个连续的调查体验：

问题：优化后 RMSNorm 精度异常

目标：定位误差来源，验证候选根因

主视图：输出 Tensor 误差对比

哪些位置出现异常？误差大小和分布如何？

关联视图：Pass Diff

哪项编译变换可能改变了数值行为？

关联视图：Tensor Mapping

误差位置和 Tile / Block 是否有关？

验证视图：候选修改前后对比

同输入、同容差下，修改是否消除了误差？有无其他回归？

关键是让视图围绕同一个问题逐步展开，共享对象身份和证据引用，而不是重复展示一套独立的计算图、IR 图、Tensor 图。

5. Outcome Evaluation：让 Skill 的验收从 UI 质量扩展到诊断价值
这是本轮实验方案最直接的补充。

现有 Skill 的验收可能比较关注表达准确性、布局、图元规范、交互行为和证据对应关系。

建议再加一层 UX Outcome：

评价指标

Skill 可以直接检查什么

必须通过用户实验验证什么

证据完整性

引用、来源、版本、验证状态是否齐全

这些证据是否足以支持正确判断

信息效率

是否突出异常、减少冗余、按需展开

用户是否更快定位到有效证据

决策可操作性

是否提供相关参数和下一步动作

用户能否有效纠正 Agent

诊断正确性

结论是否满足证据约束，验证步骤是否存在

根因正确率及错误归因率

开发效率

是否具备 CLI ↔ View 的状态传递

正确根因定位时间是否缩短

我会特别强调：Skill 自检只能验证设计规则是否执行，不能替代真实开发者的效率实验。

三、具体应该怎样改 Skill 架构？
不建议把所有新内容塞进一个巨大的 SKILL.md。可以在已有研究与设计 Skill 基础上增加一个专门的诊断工作流层。

AI Infra Skill System

ai-infra-investigation

问题定义、证据采集、根因假设、证据分级、验证与结论约束。

已有基础 · 补充 Evidence Contract
Design Spatial System / Visualization Patterns

图元、空间布局、视觉规范、联动规则和可视化表达。

已有基础 · 补充诊断视图组合
agent-diagnostic-workflow（建议新增模块）

Visualization Trigger、Decision Checkpoint、CLI ↔ View 上下文交接、结果验证与停止条件。

新增能力
diagnostic-evaluation（建议新增模块）

真实问题案例集、根因真值、A/B/C 对照、评价指标与问题类型覆盖率。

新增评估方法
这些是建议的逻辑模块，不要求立刻拆成四个独立 Skill。第一步可以通过现有 Skill 的引用文件和工作流规则扩展，避免引入额外的调用复杂度。

四、建议更新后的 Skill 目标定义
这是我认为最适合沉淀到 Skill 说明、README 或对外介绍中的版本。

AI Infra Agent-Native Visualization & Observability
Goal

Build an agent-native visualization and observability capability for AI infrastructure development, enabling coding agents to investigate complex system behavior and developers to make accurate, evidence-based decisions at critical moments.

Core capabilities

Problem-driven visualization: Identify when visual representation provides additional diagnostic value over text, logs, or automated agent execution.

Evidence-grounded diagnosis: Connect source code, compiler artifacts, runtime traces, performance metrics, and validation results while preserving provenance and uncertainty.

Human-in-the-loop investigation: Generate focused, interactive diagnostic views at decision checkpoints, allowing developers to inspect evidence, adjust parameters, challenge hypotheses, and guide subsequent agent actions.

Composable visual system: Reuse consistent objects, visual semantics, spatial patterns, and interactions across operator development, model training, and inference.

Measurable developer value: Evaluate whether visualization improves verified root-cause localization time, diagnostic accuracy, and the effectiveness of human intervention.

Design principle

Visualize when human judgment benefits from seeing relationships, differences, or execution behavior. Let agents handle routine data processing and investigation. Preserve human control over consequential decisions.

Long-term direction

An AI-native observability experience that combines the depth of a profiling tool with the adaptability of a coding agent.

五、我会优先改哪三个地方？
01

先补可视化触发条件和停止条件

这是影响 Agent 是否生成大量无效页面的关键约束。明确：什么问题直接文本回答、什么问题需要图表、什么情况下应该停止继续展开。

02

再补每类诊断问题的最低证据和验证标准

首先覆盖算子开发的精度异常、性能回归、编译变化、访存边界四类 Pattern。它们可以直接复用你已经在探索的 RMSNorm、Reduce Memory Access Check 和 Pass 相关 Demo。

03

最后把其中一个 Demo 做成 Agent 闭环，而非独立页面

以一次真实的 CLI 诊断任务为输入，让 Agent 收集证据、产生视图、接收人的操作反馈、继续调查并完成验证。然后与纯 CLI 和结构化文本方案做对照。

六、一个更深层的变化：Skill 评价对象也要改变
以前你可能会问：

“这个 Skill 能不能生成准确、美观、符合 Design System 的算子可视化？”

现在还应该追问：

“如果没有这个可视化，开发者能否同样快速、准确地完成任务？”

这是区别专业可视化能力与真正有产品价值的可观测性能力的核心问题。

例如：

如果 Agent 直接输出某个 Shape 存在越界，并附上准确的代码位置与复现测试，用户已能完成判断，就不必强制生成 Tile 网格图。

如果 Agent 只能确认特定 Shape 存在异常，但难以解释多个 Tile、Mask 和地址范围的关系，网格映射就可能显著降低人工验证成本。

如果 Agent 已经生成一张图，却无法说明图中的对象来自源码推导、编译后分配还是实际设备 Trace，那么表达越逼真，反而越可能误导用户。

因此，我建议把整个体系的最高目标更新为：

让 Agent 自主完成可自动化的调查，并在人的判断最有价值的地方，生成最少但足够准确、可验证、可操作的可视化。

这比单纯打造「AI 时代的 Perfetto」更精确：Perfetto 式的时间线、对象关系和执行证据仍然是重要基础，但产品最终服务的是 Agent-mediated Investigation（Agent 中介的问题调查），而不是让用户重新承担大量手动探索工作。

它也给你当前 Skill 的持续优化建立了清晰方向：未来不是以增加多少可视化 Pattern 为主要成果，而是以能够支持多少类真实问题、多少条可靠证据链、多少个有效人机协作节点，以及是否真正改善开发者诊断表现来衡量。
